# V1.5 生产运行问题修复报告（Phase 2-10 交付）

> 对应根因审计：`docs/V1.5_RUNTIME_ISSUE_ROOT_CAUSE.md`。
> 基线 304 passed → 修复后 **328 passed / 0 failed**（全量 `tests/`，排除既有挂起的 test_capability_acceptance.py；新增 24 个回归测试）。

## 问题 1：Task 配置成功后没有通知用户

**根因**：通知与 agent run 生命周期耦合——"任务已配置"没有独立出口，用户要等 run 结束（含最长 1900s 同步等待）才收到第一条回复。

**修改**：
- Phase 4：`run_capability` 默认异步——创建任务 + 派发后立即返回 `{task_id, status: "CONFIGURED", note}`（server/app/agent/tools/capability.py），agent 随即回复"任务已配置，完成后主动通知"。
- `AgentRun.task_id` 关联在创建时即打通（`AgentRunService.set_task`，经 `app/agent/tools/context.py` 的 ContextVar 注入 run_id）。

**验证**：`test_run_capability_async_returns_configured_and_links_run`——无 worker 在线时仍立即返回 CONFIGURED，且 run 行已带 task_id。

## 问题 2：Worker 忙线/僵尸 → 新 Task 永久卡 ACCEPTED

**根因**：① worker 的 accept 上报先于入队，消费者被僵尸占用时队列无限堆积；② 停等中的下载协程对 cancel 免疫（cancel 只在 artifact 之间检查、从不 task.cancel、无协程引用）；③ 服务端对 ACCEPTED 无活性探测、对"终态任务的非终态 attempt"无对账、cancel 投递失败静默。

**修改**（Phase 2）：
- Worker（client/worker/manager.py）：消费者取出队列任务时若 cancel 已置位 → 不执行，直接记 CANCELLED 并上报（堵死"ACCEPTED 后永不运行"）；同 attempt 重复派发按真实阶段回显（queued → accept，不再谎报 running）。
- Server（task/service.py + monitor.py）：新增 `reconcile_terminal_attempts` 对账清扫——被取代的 attempt 立即 STALE；终态任务下仍存活的 attempt，先在 `TASK_CANCEL_RESEND_WINDOW`（默认 600s）内重投停止指令（每次投递去重，投递失败继续重试），窗口过后置 STALE 并记 `task.attempt_reconciled` 事件；`_send_cancel` 投递失败显式告警。
- SENT 且设备掉线的任务按 offline max wait 提前 TIMEOUT（可重试），不再等满整个 timeout。
- PENDING 离线窗口改用 `tasks.pending_since`（migration 0008）——create/retry/所有 dispatcher 回滚都重置窗口，修复"retry 后老任务被 created_at 秒判超时"。

**验证**：`tests/agenthub/test_lifecycle_reconcile.py`（8 用例：窗口内重投/窗口后 STALE/被取代即 STALE/正常任务不受影响/只投一次/不可投不记已投/retry 窗口重置/SENT 掉线有界超时）。生产对照：重派任务不会再复现 17:45 的永久 ACCEPTED。

## 问题 3：Task 运行结束没有主动通知用户

**根因**：`notify_task_terminal` 广播已存在但只有 workflow 订阅；Task→AgentRun→钉钉会话关联字段齐备却无人打通。

**修改**（Phase 3）：
- 新增 `app/agent/notify.py`：订阅终态广播；按 task_id 反查 AgentRun；**仅当 run 已结束**（agent 先于任务放弃）才推送——run 仍在运行说明 agent 同步等待中，结果由 agent 自己带出，避免双重打扰；幂等键 `(task_id, status)` 保证一个终态只发一次；sessionWebhook 过期等推送异常只记日志。
- SUCCESS 携带产物数量与"回复『把 task_id 下载到 <目录>』"引导；FAILED/TIMEOUT 携带最后一次 attempt 的错误尾部（V1.5 已保留 tail）。
- `request_cancel` 补发终态广播（原先 admin 取消不走通知）。
- main.py 在 tool_agent 模式安装 notifier。

**验证**：`tests/agenthub/test_agent_notify.py`（3 用例：run 已结束→收到一次取消通知且重复广播不再发；run 仍在运行→零推送）。

## 问题 4：中台进度落后于子电脑实际进度

**根因**：worker 进度上报 fire-and-forget（断连即丢）；服务端 progress 事件无 seq/单调性，旧事件可覆盖新事件，中台只能扫事件流。

**修改**（Phase 8）：
- Worker：progress 闭包携带每 attempt 单调递增 `seq`（manager.py）。
- Server：attempt 新增 `progress_seq/progress_json`（migration 0009）；`task.progress` 处理仅在 `seq > 已存` 时刷新快照（无 seq 的旧 worker 兼容为 payload 更新）；`GET /api/tasks/{id}` 的 attempts[] 直接暴露 `progress` 快照——中台/agent 读快照，永不回退。
- Phase 7 的上传/下载修复同时消除了"事件循环阻塞导致 progress 延迟发送"的来源。

**验证**：`tests/agenthub/test_phase8_progress.py`（3 用例：seq=2 不覆盖 seq=3、seq=4 推进、无 seq 兼容 + API 快照；worker seq 严格递增）。

## 问题 5：AGENT_MAX_TOOL_CALLS 太小（架构问题）

**根因**：长任务等待被塞进 LLM Tool Loop，轮询耗光预算（生产 9 次全烧在 get_task_detail 上，save_artifact 没执行）。

**修改**（Phase 4）：
- `run_capability` 默认 `wait=False`：创建即返回 CONFIGURED，Tool Loop 不再为等待付费；`wait=True` 保留旧同步语义（供短任务/显式要求）。
- 任务结果由问题 3 的通知层主动推送（含 artifacts）；save_artifact 所需的 artifact_id 也在通知中可追溯（task.artifact_ids 已回填）。
- 工具描述同步更新；`waits_task=True` 保留（started_at 重基对异步路径无害、对 wait=True 必要）。

**验证**：`test_run_capability_async_returns_configured_and_links_run` + 既有同步路径测试全部改走显式 `wait=True` 且保持绿。

## 问题 6：Event.wait 泄漏（52 条 "Task was destroyed but it is pending"）

**根因**：`asyncio.wait_for(asyncio.shield(event.wait()), 10s)`——shield 使 wait_for 超时只取消外壳，内层 Event.wait Task 留存 pending；每 10 秒轮询泄漏一个，事件永不 set 的等待被 GC 一次性回收（生产 17:10:29 爆发 52 条）。加重因素：fire-and-forget `create_task` 无强引用（CPython 对 Task 仅弱引用）。

**修改**（Phase 5）：
- 三处 shield 全部移除（agent/tools/task.py、tools/workflow.py、mvp/graph.py）：`wait_for(event.wait(), timeout)` 超时即取消 waiter 本身，语义正确、零残留；事件本身支持任意多轮重复等待。
- 新增 `app/core/background.py#spawn()`：强引用 + 完成自动释放；替换全部 11 个 fire-and-forget 调用点（api/tasks、api/devices、api/workflows、api/websocket、agent/service、mvp/service）。
- 客户端 manager.bind 的 flush 任务同样落引用（manager.py `_flush_task`）。

**验证**：`tests/agenthub/test_phase5_event_lifecycle.py`（5 轮超时轮询后事件循环内 Event.wait 残留任务数为 0；spawn 引用保留/释放）。

## 问题 7：大文件下载看门狗缺失（P0）

**根因**：httpx 分阶段超时只约束相邻两次读——滴漏连接永不触发；无 stall/total 预算、无 cancel 通道；`response.content` 全量进内存、sha256 算两遍、`write_bytes` 全量落盘。

**修改**（Phase 6，downloader/puller/uploader 全部重构）：
- 下载：`client.stream()` 1MB 分块流式；每块增量 sha256（顺带消灭双重哈希与全量内存）；**stall 看门狗**（`DEVICELINK_DL_STALL`，默认 90s 无块 → `ArtifactDownloadStalled`）与**总预算**（`DEVICELINK_DL_TOTAL`，默认 900s，跨重试连续计算 → `ArtifactDownloadTimeout`）合并进同一次 `asyncio.wait`（总预算即使没有块边界也准时触发）；cancel 事件与 chunk 竞速——停等中的下载可被立即取消（打通问题 2 的取消通道）；`.part` 临时文件 + `os.replace` 原子落盘；缓存命中校验的 `sha256_file` 移入线程。
- 上传：整体移入 `asyncio.to_thread`（同步 httpx + 同步文件读，数据面彻底离开事件循环），总预算 `DEVICELINK_UL_TOTAL`（默认 900s）。
- 拉包：与下载同构（流式 + 双看门狗 + cancel + 增量哈希）。
- 成功语义：HTTP 200 ≠ 成功；200 + 完整 body + checksum 一致才算完成（checksum 不匹配不重试，§54 保持）。

**验证**：`tests/agenthub/test_phase6_download_watchdog.py`（6 用例：滴漏死链 → Stalled 有界失败；恒速滴漏 → Total 预算先触发；下载中途 cancel 立即取消；20MB 传输 checksum 一致且事件循环 ticker 最大间隙 <2s；上传离环 + 总预算；checksum 不匹配仍单请求不重试）。

## 问题 8：事件循环被大文件 IO 阻塞（含心跳独立性）

**根因**：cache-hit `sha256_file`（数百 MB 在循环上哈希）、响应体双次全量哈希、全量落盘、上传同步文件读、`subprocess.Popen`、`rglob` 目录扫描——全部跑在心跳所在的循环线程上，大文件处理时 keepalive 协程无法调度（生产 1011 keepalive ping timeout）。

**修改**（Phase 7）：
- 下载/拉包哈希改为分块增量（每块 ~1MB ≈ 数 ms，无感）；缓存校验与 stdout/stderr/context/params 落盘、Popen、输出目录扫描全部 `asyncio.to_thread`；上传整体入线程。
- 心跳（websockets 内置 ping + 业务心跳）与数据面从此物理隔离：控制面协程永不再执行大文件操作。

**验证**：Phase 10 压测（scripts/stress_bigfile.py）：100MB/500MB/1GB 三档上传+下载，**事件循环最大间隙 47ms**（1GB 下载 186 MB/s、上传 591 MB/s），checksum 全部一致。
