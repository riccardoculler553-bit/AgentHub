# AgentHub V1.1 开发架构文档

> 版本：AgentHub V1.1
> 基线：AgentHub V1.0 + MVP-Real-1.0 + Routing-1.0
> 定位：Reliable Task Execution / Reliable Task Engine
> 核心目标：在不推翻 V1.0 架构的前提下，解决任务状态一致性、Attempt 竞争、重复派发、超时、取消、晚到结果、断线恢复、幂等、安全与审计问题。

---

# 1. V1.1 的定位

AgentHub V1.0 已经完成了第一阶段最重要的事情：

```text
钉钉
  ↓
Main Agent
  ↓
Command / Device Routing
  ↓
Task
  ↓
DeviceLink
  ↓
Worker
  ↓
影刀
  ↓
Task Result
  ↓
钉钉回复
```

当前 V1.0 的核心任务模型已经包含：

```text
Task
TaskStep
TaskAttempt
TaskEvent
```

DeviceLink 已具备：

```text
设备注册
Device Token
WebSocket
Heartbeat
Reconnect
ConnectionHub
task.dispatch
task.accept
task.running
task.progress
task.result
task.cancel
```

Worker 侧已经存在：

```text
ExecutionLedger
Attempt 幂等记账
运行态恢复
断线后结果补报
影刀 Executor
```

因此 V1.1 **不是重新设计 AgentHub**。

V1.1 的目标只有一句话：

> **让一个任务无论遇到重复派发、并发竞争、超时、取消、晚到结果、Server 重启、Worker 重启、WebSocket 重连，都不会把任务状态搞乱。**

# 2. V1.1 核心原则

## 2.1 不推翻现有四层架构

保持：

```text
┌──────────────────────────────────────────────┐
│ Reasoning Plane                              │
│ Main Agent / LangGraph                       │
├──────────────────────────────────────────────┤
│ Control Plane                                │
│ Task / Attempt / Command / Capability        │
├──────────────────────────────────────────────┤
│ Communication Plane                         │
│ DeviceLink / WebSocket / ConnectionHub       │
├──────────────────────────────────────────────┤
│ Execution Plane                              │
│ Worker / Executor / Yingdao                  │
└──────────────────────────────────────────────┘
```

V1.1 主要改造：

```text
Control Plane
Execution Plane
```

Communication Plane 只做必要的连接和投递增强。

Reasoning Plane 不进行大规模重构。

# 4. V1.1 任务模型

AgentHub 的核心执行对象明确分成：

```text
Task
  ↓
Step
  ↓
Attempt
```

关系：

```text
Task
├── Step 1
│    ├── Attempt 1
│    ├── Attempt 2
│    └── Attempt 3
│
├── Step 2
│    └── Attempt 1
│
└── Step 3
     └── Attempt 1
```

定义：

### Task

用户真正提交的一次业务任务。

例如：

```text
运行办公室电脑02的 Text1
```

对应：

```text
task_id = xxx
```

### Step

Task 中的一个执行步骤。

V1.1 仍然支持单 Step 为主。

例如：

```text
step_id = xxx
command = yingdao.audit
device_id = device-02
```

### Attempt

Step 的一次实际执行尝试。

例如：

```text
attempt_1
timeout
↓
attempt_2
success
```

核心原则：

> **Step 是逻辑执行单元，Attempt 是物理执行单元。**

# 6. 终态不可逆

以下状态属于 Task 终态：

```text
SUCCESS
FAILED
CANCELLED
TIMEOUT
```

进入终态后：

```text
SUCCESS   ─X→ RUNNING
SUCCESS   ─X→ FAILED
SUCCESS   ─X→ TIMEOUT

FAILED    ─X→ RUNNING
CANCELLED ─X→ RUNNING
TIMEOUT   ─X→ SUCCESS
```

除非显式创建新的 Retry Attempt。

核心原则：

> **晚到结果不能重新打开一个已经结束的任务。**

---

# 7. Current Attempt 是 V1.1 核心

V1.0 最大的问题之一是：

```text
Attempt 1
  ↓
TIMEOUT

Attempt 2
  ↓
RUNNING

Attempt 1
  ↓
late result = SUCCESS
```

如果只根据：

```text
task_id
step_id
```

寻找 Task，那么 Attempt 1 的结果可能错误地修改 Attempt 2。

V1.1 必须建立：

```text
Step
  ↓
current_attempt_id
```

或等价机制。

逻辑必须是：

```text
Step
├── attempt_1
├── attempt_2
└── current_attempt = attempt_2
```

收到：

```json
{
  "task_id": "...",
  "step_id": "...",
  "attempt_id": "attempt_1"
}
```

必须判断：

```text
attempt_id == current_attempt_id ?
```

不是：

```text
record event
ignore state mutation
```

而不是：

```text
直接更新 Step
```

---

# 8. Late Event 处理原则

所有设备事件统一按照：

```text
解析事件
↓
验证 Task
↓
验证 Step
↓
验证 Attempt
↓
判断是否 Current Attempt
↓
判断当前状态是否允许转换
↓
更新状态
↓
记录 Event
```

如果：

```text
attempt_id != current_attempt_id
```

则：

```text
事件继续记录
但禁止修改当前 Task / Step / Attempt 状态
```

Event 可以标记：

```text
is_stale = true
```

或者通过 event_type：

```text
task.result.late
```

均可。

V1.1 最低要求是：

> **晚到事件可审计，但不能污染当前状态。**

---

# 9. Attempt 状态模型

Attempt 建议：

```text
CREATED
DISPATCHING
SENT
ACCEPTED
RUNNING
SUCCESS
FAILED
CANCELLED
TIMEOUT
STALE
```

其中：

```text
STALE
```

不是实际执行失败，而是：

```text
这个 Attempt 已经不是当前执行上下文
```

例如：

```text
Attempt 1 TIMEOUT
Attempt 2 RUNNING

Attempt 1 later SUCCESS
```

Attempt 1：

```text
TIMEOUT → STALE_RESULT
```

不能：

```text
Task → SUCCESS
```

---

# 10. Dispatcher 并发竞争

当前 Dispatcher 不允许：

```text
线程 A:
读取 Task=PENDING

线程 B:
读取 Task=PENDING

线程 A:
创建 Attempt 1

线程 B:
创建 Attempt 2
```

导致：

```text
同一个 Task
↓
两个 Attempt
↓
两个 Worker Dispatch
```

V1.1 必须保证：

> **PENDING → DISPATCHING 是原子竞争。**

推荐：

```sql
UPDATE tasks
SET status = 'DISPATCHING'
WHERE task_id = :task_id
  AND status = 'PENDING';
```

检查：

```text
affected_rows == 1
```

才允许继续。

如果：

```text
affected_rows == 0
```

说明：

```text
已经被其他线程抢走
```

当前 Dispatcher 立即结束。

---

# 11. Dispatcher 新流程

```text
dispatch_task(task_id)
        │
        ▼
读取 Task
        │
        ▼
PENDING?
   │          │
   │否       是
   ▼          ▼
 return   atomic claim
              │
              ▼
       DISPATCHING
              │
              ▼
       创建 Attempt
              │
              ▼
       更新 SENT
              │
              ▼
      ConnectionHub
              │
              ▼
       send_task()
```

只有成功抢到：

```text
PENDING
```

的执行者可以创建当前 Attempt。

---

# 12. Worker 端 Attempt 竞争

Worker 端存在：

```text
task_id + step_id
```

逻辑执行槽。

同一个：

```text
task_id
step_id
```

同时只能存在一个 Active Execution。

例如：

```text
task-A
step-1
```

不能同时：

```text
attempt-1 running
attempt-2 running
```

所以 Worker 收到新的：

```text
task.dispatch
```

先检查：

```text
(task_id, step_id) 是否已 active
```

再进行：

```text
ledger.claim()
```

不能反过来。

---

# 13. Worker Dispatch 顺序

正确顺序：

```text
收到 task.dispatch
        │
        ▼
解析 task_id / step_id / attempt_id
        │
        ▼
检查 active task/step
        │
   ┌────┴─────┐
   │          │
 已存在       不存在
   │          │
   ▼          ▼
拒绝/幂等     ledger.claim
                 │
                 ▼
             active 注册
                 │
                 ▼
              执行
```

如果已经存在相同：

```text
task_id
step_id
attempt_id
```

则视为重复派发：

```text
不要重新执行
```

如果：

```text
task_id + step_id
```

已经有其他 Attempt 在运行：

```text
不要新增一个孤儿 Ledger Attempt
```

---

# 14. Task Timeout

V1.1 不再只把：

```text
task.timeout_at
```

作为唯一依据。

核心超时对象是：

```text
Attempt
```

例如：

```text
Task timeout = 300s
Attempt 1 started = 10:00
Attempt 1 timeout = 10:05
```

Retry：

```text
Attempt 2 started = 10:06
Attempt 2 timeout = 10:11
```

不能让 Attempt 1 的 timeout 影响 Attempt 2。

---

# 15. Timeout 处理

TaskMonitor：

```text
扫描当前运行 Attempt
        │
        ▼
current_attempt.timeout_at < now ?
        │
       是
        ▼
原子更新 Attempt = TIMEOUT
        │
        ▼
确认仍是 current_attempt
        │
        ▼
Task = TIMEOUT
        │
        ▼
发送 task.cancel
```

如果在发送取消之前：

```text
Worker 已经 SUCCESS
```

则不应该再：

```text
Task → TIMEOUT
```

所以 Timeout 更新本身也必须有状态条件。

---

# 16. Cancel 必须绑定 Attempt

V1.0：

```text
task.cancel
{
    task_id
}
```

存在风险。

例如：

```text
Attempt 1
TIMEOUT

Attempt 2
RUNNING
```

此时发送：

```text
task.cancel(task_id)
```

Worker 可能无法判断取消的是谁。

V1.1：

```json
{
  "type": "task.cancel",
  "task_id": "...",
  "step_id": "...",
  "attempt_id": "..."
}
```

Worker：

```text
只有当前 active attempt_id
==
收到的 attempt_id
```

才真正执行取消。

---

# 17. Cancel 的设备目标也必须固定

不能：

```text
task.cancel
↓
send_to_device()
↓
广播到所有设备连接
```

应该：

```text
Task
 ↓
current Attempt
 ↓
target_device_id
 ↓
selected worker connection
 ↓
task.cancel
```

也就是说：

> Cancel 是“取消当前执行实例”，不是“广播一个任务取消通知”。

# 18. Task Event 审计

V1.0 已经存在：

```text
task_events
```

V1.1 必须让 Attempt 上下文完整。

以下 Event 必须记录：

```text
task.created
task.dispatching
task.dispatched
task.accepted
task.running
task.progress
task.result
task.cancel_requested
task.cancelled
task.timeout
task.retry
task.late_result
task.failed
```

涉及 Attempt 的事件：

```text
必须带：
task_id

```

不能出现：

```text
task.running

```

否则以后无法准确恢复执行时间线。

# 20. AgentRun 状态修正

当前 AgentRun 逻辑如果：

```text
Task = TIMEOUT
```

最终可能统一映射：

```text
AgentRun = FAILED
```

V1.1 改为：

```text
Task SUCCESS
    ↓
AgentRun SUCCESS

Task FAILED
    ↓
AgentRun FAILED

Task TIMEOUT
    ↓
AgentRun TIMEOUT

Task CANCELLED
    ↓
AgentRun CANCELLED
```

至少不能把：

```text
TIMEOUT
CANCELLED
```

全部压扁成：

```text
FAILED
```

# 21. AgentRun 幂等

DingTalk 同一个消息可能重复进入。

当前逻辑：

```text
SELECT message_id
↓
不存在
↓
INSERT
```

存在并发竞态：

```text
Request A SELECT 不存在
Request B SELECT 不存在
Request A INSERT
Request B INSERT
```

V1.1：

数据库增加：

```sql
UNIQUE(channel, message_id)
```

或者：

```sql
UNIQUE(message_id)
```

根据现有消息模型确定。

代码逻辑：

```text
try:
    create AgentRun
except IntegrityError:
    query existing AgentRun
    return existing
```

数据库唯一约束是最终保证。

V1.0 已设计：

```text
Admin Token
Device Token
```

但 V1.1 必须统一检查管理接口。

以下接口：

```text
GET /api/devices
POST /api/devices/{device_id}/revoke
GET /api/devices/{device_id}

```

必须：

```text

```

唯一允许公开的设备接口：

```text

```

```text
Registration Code
```

# 23. WebSocket 安全

设备 WebSocket：

```text

```

必须验证：

```text

```

并检查：


```text

```

```text
4403
```

```text

```

# 27. Command 与实际代码的关系

必须明确：

```text
Command ≠ Python 文件
```

Command 表示：

> AgentHub 允许执行什么。

实际代码：

> Worker 上具体如何执行。

例如：

```text
command:
yingdao.audit
```

Worker：

```text
Work/
└── yingdao_audit/
    └── main.py
```

AgentHub 不直接知道：

```text
main.py
D:\xxx\xxx.py
```

Agent 不允许提交：

```json
{
  "path": "D:\\xxx\\evil.py"
}
```

路径仍然由 Worker 本地命令注册表控制。

# 33. Worker 结果处理流程

Server 收到：

```text
task.result
```

严格执行：

```text
1. 找 Task
2. 找 Step
3. 找 Attempt
4. 检查 Attempt 是否存在
5. 检查 Attempt 是否 current
6. 检查 Task 是否 terminal
7. 检查 Step 是否 terminal
8. 检查 Attempt 是否 terminal
9. 写 Event
10. 状态转换
11. 唤醒 waiter
```

# 44. Monitor 的重要原则

Monitor 不是状态“随便修改器”。

所有状态修改都必须使用：

```text
conditional update
```

例如：

```sql
UPDATE task_attempts
SET status = 'TIMEOUT'
WHERE attempt_id = :attempt_id
  AND status = 'RUNNING';
```

只有：

```text

```

才表示：

```text

```

否则：

```text
状态已经被其他线程修改
```

直接停止。

# 56. V1.1 验收标准

必须达到：

```text
① 同一 Task 不会被并发 Dispatch 多次

② 同一 Step 不会出现多个同时 Active Attempt

③ 老 Attempt 结果无法覆盖新 Attempt

④ TIMEOUT 后晚到 SUCCESS 不会恢复任务

⑤ CANCEL 后晚到 SUCCESS 不会恢复任务

⑥ Task terminal 后任何普通 Event 都不能重新打开 Task

⑦ Cancel 必须绑定 current attempt

⑧ Timeout 必须绑定 current attempt

⑨ Worker 重复 Dispatch 不会重复执行

⑩ AgentRun message_id 有数据库级幂等保证

⑪ Device 管理 API 全部受 Admin Auth 保护

⑫ 生产环境由 Alembic 管理 Schema

⑬ Worker 断线后能够补报本地未上报结果

⑭ Server 重启不会无条件重复派发

⑮ 所有任务生命周期 Event 都能追踪到 Attempt
```

# 71. V1.1 失败处理原则

任何出现：

```text
异常
数据库竞争
重复事件
过期 Attempt
```

都遵循：

```text
记录
↓
不污染当前状态
↓
保持最终状态一致
```

而不是：

```text
为了“看起来执行成功”
强行把 Task 改 SUCCESS
```

# 74. V1.1 最终目标

V1.0 解决的是：

> **“AgentHub 能不能真正把任务跑起来？”**

V1.1 解决的是：

> **“AgentHub 在真实生产环境里遇到各种异常后，还能不能保证任务状态是正确的？”**

因此 V1.1 完成以后，系统应该能够明确回答：

```text
这个任务是谁创建的？
哪个 Step？
哪个 Attempt？
哪个设备？
哪个 Worker？
什么时候派发？
什么时候接受？
什么时候开始？
有没有超时？
有没有取消？
是否重试？
当前 Attempt 是谁？
这个结果是不是当前 Attempt？
任务为什么成功/失败？
Worker 是否重复执行过？
Server 重启后发生了什么？
```

并且这些信息都能够从：

```text
Task
Step
Attempt
Event
ExecutionLedger
```

中还原出来。

# 76. V1.1 一句话总结

AgentHub V1.1 不增加大量新功能。

而是把现在：

```text
“一个能跑通的 Agent + RPA 系统”
```

升级成：

```text
“一个真正可靠的任务执行控制平面”
```

核心关系最终固定为：

```text
Agent
 ↓
Task
 ↓
Step
 ↓
Current Attempt
 ↓
Worker
 ↓
Executor
 ↓
Result
```

其中：

```text
Task = 业务任务
Step = 逻辑步骤
Attempt = 一次真实执行
Worker = 哪台电脑
Executor = 怎么执行
Event = 发生过什么
```

这套模型将直接支撑后面的：

```text
V1.2 Task Package / Version
V1.3 Workflow
V2 Multi-device
V3 Sandbox
V4 Multi-Agent
```

而无需推翻 V1.1 的核心执行模型。
