# AgentHub v1.6 Product Roadmap

> **Status:** design only (no Service runtime code in this PR).
> **Baseline:** V1.5 Remote-Exec-1.0 + Lifecycle-1.0, git `main` @ `5022651`.
> **Audience:** product / ops owners deciding *what to build next*, and engineers mapping those bets onto this repo.
> **One-line intent:** turn AgentHub from an engineer-operated control stack into a **product service** that ops, RPA, and data teams can run on a fleet of office PCs.

This is a **product plan**, not a single-feature spec. Long-running Python on a designated PC is **one capability** among many. It is not the center of v1.6.

---

## 0. Executive summary

AgentHub already has a production-grade **control plane** (CAS task engine, DeviceLink WebSocket, capability packages, HTTP artifact plane, LangGraph tools, DingTalk). What it does *not* yet have is the **product layer** that makes that plane usable by non-authors: tenant/admin UX, fleet health, a capability catalog, run history that operators trust, alerts that fire without someone grepping logs, packaging that survives a Windows reboot, and security defaults that fail closed.

v1.6 should ship as **five parallel workstreams**, not a rewrite:

| Workstream | Why it exists | Shape |
| --- | --- | --- |
| **A. Reliability productization** | V1.5 production incidents still have open tails (ACCEPTED zombies, upload OOM, dirty WS disconnects, DEVICE_BUSY semantics) | Harden existing `task/`, `artifact/`, `websocket/`, `worker/` |
| **B. Operator surfaces** | Dashboard is a five-tab engineer console; Workflows, capability versions, alerts, and unified run history are API-only or missing | Extend `server/app/static/index.html` + APIs |
| **C. Supervised processes** | One-shot Task ≠ a process that should stay up; Worker itself is a foreground Python console | **New** `process/` plane (greenfield) + Worker OS-service installer |
| **D. Trust & tenancy** | Single shared admin token, fail-open auth, any-device-can-download-any-blob | `auth/`, artifact/package ACL, roles |
| **E. Time-to-first-device** | First Worker today is MySQL + Alembic + Funnel + JSON alignment | Packaging, wizard, health checks |

**What “productized” means for this buyer:** an ops lead can enroll a PC in ten minutes, see it healthy, pick a versioned capability, run it against named data, get a completion/failure alert, download the file, and restart a stuck worker — without opening this git repo.

## 1. Product framing

### 1.1 Who buys, who uses

| Role | Job | Today they… |
| --- | --- | --- |
| **Buyer (ops / RPA lead)** | Keep Excel / 影刀 / Python jobs running on office PCs without a dedicated SRE | Copy `client/`, edit `capabilities.json`, babysit ACCEPTED tasks in DingTalk |
| **Operator (data / finance / audit)** | Kick a preprocess or RPA robot, get a file back, know if it failed | @ the robot and wait; or ask the engineer who has the admin token |
| **Capability author (engineer)** | Package a Python/Yingdao job so others can run it | ZIP + manifest + POST versions; no catalog UI |
| **Device owner (the PC on the desk)** | Leave the machine on; not think about Python processes | Runs `python client/main.py` in a console that dies on logout |

This is **not** a Kubernetes product. The unit of compute is a **named Windows (or office) PC** that already has Excel, 影刀 (ShadowBot), local disks, and no inbound ports. The 2026-09-15 production incident (东方神舟 / 星舰X / 地平线1号 / 长征七号) is the actual fleet shape: a handful of designated PCs, large xlsx artifacts, concurrent preprocess, human waiting in a DingTalk group.

### 1.2 Jobs to be done

1. **“Run this job on *that* PC, not a random container.”** Named device, not a pool by default. (`Task.target_device_id`, `run_capability(device=…)`, `CapabilityResolver` explicit-worker-first.)
2. **“Move a 500MB spreadsheet to the PC, run, bring the result back.”** Artifact plane, not attachments in the chat.
3. **“Don’t make me re-copy scripts when the job changes.”** Versioned capability packages + lazy pull.
4. **“If the PC is busy or half-dead, tell me — don’t hang for 30 minutes.”** Fleet semantics: DEVICE_BUSY, ACCEPTED liveness, heartbeats.
5. **“When it’s done (or dead), ping the group — don’t make me poll.”** Notification plane independent of the LLM loop.
6. **“Keep the worker alive across reboot / logout, and let me restart a long job.”** Missing today. This is the process/daemon workstream — **one** JTBD, not all of them.
7. **“I am not the person who wrote AgentHub.”** Onboarding, Dashboard, roles.

### 1.3 What must feel productized vs the current engineer-operated stack

| Surface | Engineer-operated today | Productized v1.6 |
| --- | --- | --- |
| Enroll a device | POST registration code, `python client/main.py --code`, identity in `~/.devicelink` | Installer / one-liner + Dashboard “Add device” wizard |
| Worker lifetime | Foreground console (`client/main.py`) | OS service / scheduled task; start on login; crash restart |
| What can run | `capabilities.json` must **character-match** `commands` table (LEARNING_GUIDE §1.2) | Catalog: published capability versions, pin per device |
| Data in/out | `scan?dir=` + `register-local` of a **server** path; `save_artifact` writes to another server path | Named datasets, device-local folders, download links for humans |
| Progress | Attempt `progress_json` exists; Dashboard is a raw task table | Run history with latest progress, ETA, last error |
| Failure | Engineer reads `server/logs/server.log` + `client/logs/worker.log` | Alert: stalled ACCEPTED, download stall, DEVICE_BUSY, offline |
| Auth | `AGENTHUB_ADMIN_TOKEN` empty = **open** (`auth/admin.py`) | Fail-closed; roles (admin / operator / device) |
| Channel | DingTalk Stream + HTTP Agent API | Same channels, plus Dashboard as the system of record |

## 2. Codebase audit (what v1.6 inherits)

Facts below are from this tree. Historical docs disagree on test counts and table counts (`README.md` still says “38 tests”; `ARCHITECTURE.md` header says 299; `docs/V1.5_RUNTIME_FIX_REPORT.md` says 328). Treat **code + `docs/AUDIT_REPORT_2026-09-19.md` + V1.5 lifecycle docs** as the source of truth.

### 2.1 Four planes (real paths)

```
Reasoning    server/app/agent/          LangGraph tool agent + MVP + legacy
Control      server/app/task/           Task state machine, CAS dispatch, monitor
             server/app/workflow/       Deterministic multi-step engine
             server/app/command/        Allowed commands (system policy)
             server/app/capability/     Device-reported command capabilities (old)
             server/app/capability_runtime/  Versioned packages (V1.4)
             server/app/artifact/       HTTP data plane
Communication server/app/websocket/     DeviceLink hub, envelope, heartbeat
             server/app/device/         Registration, tokens, status
             server/app/api/websocket.py
Execution    client/                    DeviceClient + Worker
             client/worker/manager.py   Single-consumer queue, ledger
             client/worker/executors/   echo / python / yingdao
             client/worker/capability/  Lazy pull, venv, artifact IO
Channel      server/app/integrations/dingtalk/
UX           server/app/static/index.html
```

**Architecture decision to preserve:** uncertainty lives only in the Agent. Workflow and Task are deterministic state machines. Agent never touches WebSocket; the only seam is `server/app/task/device_link.py`.

### 2.2 DeviceLink (communication)

| Piece | Path | Product implication |
| --- | --- | --- |
| Device ≠ Connection | `server/app/websocket/hub.py` | Fleet UI must show **device** health, not raw sockets |
| Single worker connection for dispatch | `hub.select_worker_connection` | Extra WS connections (dashboards, probes) must not steal `task.dispatch` |
| Outbound-only clients | `client/main.py`, README network model | Office PCs behind NAT are first-class; no inbound ports |
| Heartbeat 15s / offline 45s | `client/heartbeat.py`, `server/app/websocket/heartbeat.py`, `core/config.py` | “Online” is connection + business heartbeat + `last_seen_at` |
| Reconnect with jitter | `client/reconnect.py` (`1,2,4,8,16,30s`) | Fleet reconnect storms are already considered |
| Registration | `server/app/registration/service.py`, `core/security.py` | 8-char / 40-bit codes, 5 min TTL, **no rate limit** (audit M2) |
| Token | `server/app/auth/token.py` | Hash-at-rest; revoke → WS 4403, client stops reconnect |

**Gap:** `server/app/api/websocket.py` `_dispatch` is not isolated — a bad event raises into the connection loop and closes the socket with **1011** (audit H4). Product symptom: “the PC dropped for no reason.”

### 2.3 Task engine (control)

| Piece | Path | Notes |
| --- | --- | --- |
| State machine | `server/app/task/state.py` | PENDING → DISPATCHING → SENT → ACCEPTED → RUNNING → terminal; STALE is attempt-only |
| Create / event gates | `server/app/task/service.py` | Four-way create validation; five-gate device events |
| CAS dispatch | `server/app/task/dispatcher.py` | Conditional UPDATE; exactly one winner |
| Monitor | `server/app/task/monitor.py` | PENDING redispatch, timeout_at, STALE reconcile |
| Events / waiters | `task/events.py`, `task/waiters.py` | Terminal broadcast; Workflow + Agent notify subscribe |

**Known open reliability tails (must be P0 of v1.6, not “later”):**

1. **ACCEPTED has no liveness probe.** `timeout_scan` watches SENT/ACCEPTED/RUNNING against `timeout_at` (capability default **1800s**). SENT-offline has a 600s bound; ACCEPTED does not. `attempt.accepted_at` is written and unused. Documented as unfixed in `docs/AUDIT_REPORT_2026-09-19.md` H3 and in `monitor.py` itself (“TIMEOUT is retryable, an ACCEPTED-forever state is not”). This is the 地平线1号 17:45 symptom.
2. **DEVICE_BUSY is two different products.** Legacy command dispatch **fails** the new task (`dispatcher.py` ~91–107). Capability dispatch **defers** (`PENDING`, log “deferred: worker busy”). Agent tools expose `DEVICE_BUSY` (`agent/tools/base.py`, `command.py`). Operators cannot tell “rejected” from “queued behind a zombie.”
3. **Accept ≠ running.** Worker reports accept on intake, then queues (`client/worker/manager.py`). Server ACCEPTED means “in the worker’s unbounded queue,” not “OS process exists.”
4. **`max_concurrency = 1`** is hard-wired. Correct for 影刀 GUI; product needs an explicit **busy policy** (fail / queue / overflow device) rather than a silent single lane.

### 2.4 Capability Runtime + Artifact plane

| Piece | Path | Product implication |
| --- | --- | --- |
| Definition / versions | `capability_runtime/service.py`, `db_models.py` | Immutable `(name, version)`; DRAFT → PUBLISHED → DEPRECATED |
| Manifest | `capability_runtime/manifest.py` (server) + `client/worker/capability/manifest.py` | `domain.resource.action`, semver, runtime `yingdao\|python\|http\|local` |
| Packages | `package_service.py`, `GET /api/capability-packages/{id}/download` | ZIP + checksum; lazy pull on worker |
| Resolver | `capability_runtime/resolver.py` | Explicit worker → reporters → **any online worker (lazy pull)** |
| Worker install | `client/worker/capability/manager.py`, `cache.py`, `puller.py` | Per-version lock; venv + `requirements.txt` |
| Executors | `client/worker/capability/executors.py` | Python venv subprocess; wraps Yingdao |
| Artifacts | `artifact/service.py`, `api/artifact.py` | Disk blobs; checksum dedupe per (task, step) |
| Input pipeline | dispatcher `_dispatch_capability` `input_artifacts` | WS carries **references**; HTTP carries bytes |

**V1.5 already fixed on the client data plane** (see `docs/V1.5_RUNTIME_FIX_REPORT.md`): stream 1MB chunks, stall/total watchdogs, cancel-during-download, `to_thread` so heartbeat survives 1GB. **Server uploads still `await file.read()` whole-file** (`api/artifact.py:68`, `api/capability.py` zip upload) — audit H2. Production storage was measured at tens of GB / 400–658MB xlsx.

**Security gap M1:** download endpoints authenticate *a* device token, not *this* device’s right to *this* blob (`api/artifact.py:150–162`, capability package download).

**Dashboard mismatch:** the “能力” tab calls `/api/device-capabilities` (old per-device command list), **not** `/api/capabilities` (the V1.4 catalog). There is **no Workflow tab** at all (`index.html` tabs: 设备 / 任务 / 命令 / 能力 / 数据源 / Agent).

### 2.5 Agent + Workflow

| Piece | Path | Notes |
| --- | --- | --- |
| Modes | `AGENT_MODE=mvp\|tool_agent` in `core/config.py` | Default in code is **mvp**; production runbook says set `tool_agent` |
| Tools | `agent/tools/` via `registry.py` `build_default_registry` | device / task / command / workflow / capability / artifact |
| Gates | `agent/core/policies.py` | READ/WRITE/ACTION; `AGENT_CONFIRM_ACTIONS` default **false** (audit H5) |
| Async capability | `agent/tools/capability.py` | `wait=False` → CONFIGURED; terminal via `agent/notify.py` |
| Notify | `agent/notify.py` | Only if an `AgentRun` exists **and** that run already finished; API/workflow tasks silent |
| Workflow | `workflow/engine.py`, `monitor.py`, `runtime.py` | Deterministic; CAS; `{{ steps.x.result.k }}` |
| Routing leftover | `server/config/agent_tools.json` | Still hard-codes `yingdao.audit` → `办公室电脑02` |

**Product bug, not just an agent bug:** “notification ≠ agent poll” is half-fixed. DingTalk gets CONFIGURED + (sometimes) terminal. Dashboard has no alert inbox. Workflow completions do not notify. `sessionWebhook` expiry is log-and-drop.

### 2.6 Worker + DingTalk + Dashboard

| --- | --- | --- |

## 3. Industry pain points → product features → this repo

Public automation ops literature is consistent: the hard part is not “write a bot,” it is **running a fleet of desktop workers** (health, drift, queueing, silent failure, credentials, versioning). AgentHub already chose the right *technical* split (control WS + data HTTP + packages). v1.6 is the *product* mapping of those pains onto modules.

| Industry pain | Evidence (public) | Product feature in v1.6 | Existing module | Missing / greenfield |
| --- | --- | --- | --- | --- |
| Desktop apps are **single-tenant**; one bot per machine at a time; routing/queueing becomes custom middleware | [Scaling Desktop Automation from Five Bots to Five Hundred](https://minicor.com/blog/scaling-desktop-automation-five-to-five-hundred) | Explicit busy policy: fail / queue / overflow; DEVICE_BUSY as a first-class Dashboard state | `dispatcher.py` DEVICE_BUSY; worker `max_concurrency=1`; Yingdao `EXECUTOR_BUSY` | Queue depth, overflow device, operator-visible busy reason |
| Unattended fleets need registration, grouping, health, least-busy assignment, reboot survival | [Power Automate machine management](https://www.solvingdynamics365.com/guides/power-automate-machine-management); [UiPath machine templates](https://docs.uipath.com/orchestrator/automation-cloud/latest/USER-GUIDE/optimizing-unattended-infrastructure-using-machine-templates) | Device fleet: labels, groups, worker version, last error, “maintenance mode” | `devices` table, `ConnectionHub`, `CapabilityResolver._order_by_load` | Groups, maintenance drain, installer, OS-service |
| OS updates / session / agent-not-running look like “bot bugs” | [Unattended bots failing after OS updates](https://senawe.com/how-to-troubleshoot-unattended-rpa-bots-failing-during-os-updates/) | Heartbeat + process supervisor + “worker not running” alert distinct from task FAILED | HeartbeatMonitor; ledger `WORKER_RESTARTED` | Worker-as-service; host inventory (OS, Excel, 影刀 version) |
| Selector / environment drift; 2–4 h/bot/month maintenance; 87% see bot failures | [Pega RPA survey](https://www.pega.com/about/news/press-releases/survey-most-businesses-find-rpa-effective-hard-deploy-and-maintain); [RPA TCO](https://strategypeeps.com/rpa-maintenance-the-total-cost-of-ownership-your-vendor-wont-quote/); [Swfte / Gartner ROI](https://www.swfte.com/blog/rpa-investment-roi-failure-ai-alternative) | Versioned capabilities + pin + deprecate; run history with stdout/stderr tails | `capability_versions`; attempt `progress_json`; Yingdao log-mode | Catalog UI; “this version on these devices”; diff of last success vs fail |
| Failures at volume need detection, retry, escalation — not a human staring at a dashboard | [Minicor scaling](https://minicor.com/blog/scaling-desktop-automation-five-to-five-hundred); Forrester: downtime eats RPA ROI ([CIO summary](https://www.cio.com/article/215856/4-surprising-rpa-research-findings-from-forrester.html)) | Alerts: ACCEPTED stalled, download stalled, offline, DEVICE_BUSY, checksum fail | TaskMonitor; download watchdogs; `agent/notify.py` | Alert rules, Dashboard inbox, channels beyond DingTalk |
| Agent-to-desktop: LLM should **plan**, RPA/script should **execute**; AACU is not yet as reliable as RPA for repetitive desktop | [Are LLM Agents the New RPA? (arXiv:2509.04198)](https://arxiv.org/pdf/2509.04198.pdf); [Microsoft: RPA vs CUA](https://learn.microsoft.com/en-us/windows-365/agents/when-to-use-w365a); [RPA vs AI agents 2026](https://ztabs.co/blog/rpa-vs-ai-agents-2026) | Keep “LLM in a cage”: Agent tools → Task/Workflow; no computer-use driver in v1.6 | `policies.py`, tool registry, three-engine split | Operator-facing confirmation UX (H5) |
| Moving files / artifacts between cloud agent and PC is its own product | Repo production: 400–658MB xlsx; V1.5 download stall | Dataset objects, progress of transfer, human download, retention | `artifact/` | ACL, streaming **server** IO, retention TTL UI, named datasets |
| Shadow bots, shared admin passwords, `.env` tokens, over-privileged workers | [Secure RPA 2026](https://techelix.co/blogs/secure-rpa-infrastructure-zero-trust-governance/) | Fail-closed admin, device-scoped downloads, confirm ACTION, no path-from-LLM | Token hashing; python path whitelist; `extra=forbid` | H1/M1/H5; roles; audit export |
| Packaging & versioning of what runs on the PC | RPA CoE + UiPath process versions | Capability marketplace-*ish*: publish, pin, rollback (not a store with billing) | `CapabilityService` version lifecycle | Dashboard catalog; signed packages (P2) |
| Offline / NAT workers | Power Automate / UiPath robots are outbound agents | Keep outbound WSS; cache packages; replay ledger | DeviceLink; `CapabilityCache`; ledger | Offline-enqueue with bounded disk; “last known package” |

## 4. Competitive / adjacent lenses (not a market report)

AgentHub’s wedge is **not** “another RPA designer” and **not** “another job queue.”

| Adjacent | What they optimize | What they miss for *this* buyer | What AgentHub uniquely has |
| --- | --- | --- | --- |
| **UiPath / Automation Anywhere / Power Automate Desktop** | Bot design + licensed orchestrator + unattended machine templates | Heavy CoE, license, cloud lock-in; weak “LLM talks DingTalk → designated PC → Excel file” loop | Outbound WS DeviceLink; capability ZIP + venv; DingTalk Stream; Agent tools with schema `extra=forbid` |
| **Celery / RQ / cloud job queues** | Server workers, brokers, retries | Assume data-center processes, inbound connectivity, no GUI/Excel/影刀 session | Named **devices**, busy-check against ShadowBot logs, artifact checksums |
| **Ansible** | Agentless SSH config drift | Not GUI automation; not NAT office PCs; not conversational dispatch ([UiPath vs Ansible](https://apix-drive.com/en/blog/other/uipath-vs-ansible)) | Worker pulls over WSS; RPA executor; lazy package pull |
| **Kubernetes / systemd on servers** | Container reconciliation | Foreground Windows GUI cannot live in a pod; Excel/Yingdao need an interactive (or at least local) desktop ([UiPath forum: workstation vs server](https://forum.uipath.com/t/should-uipath-run-on-a-server-or-workstation/198458); [Ansible vs k8s](https://markaicode.com/vs/ansible-vs-kubernetes/)) | Device as identity; ConnectionHub; execution on the actual PC |
| **n8n / Zapier** | SaaS API workflows | No 500MB xlsx on 办公室电脑; no 影刀 | Artifact plane + Yingdao executor |
| **Raw computer-use agents** | LLM clicks the screen | Slow, hard to audit, not production-reliable vs RPA on stable UIs ([arXiv:2509.04198](https://arxiv.org/pdf/2509.04198.pdf)) | LLM **selects** a versioned capability; execution is deterministic Task |

**Moat to double down on in v1.6 (do not dilute):**

1. **WS control + HTTP data** — “bytes never ride the chat or the WS.” (`docs/LEARNING_GUIDE_0_to_1.md` §0.2)
2. **Capability packages** — program ≠ data ≠ one run ≠ a PC.
3. **Designated Worker** — explicit device wins over clever scheduling (`resolver.py`).
4. **Agent tools as a narrow API** — 17 tools, seven gates, Task engine owns retry.
5. **Office-PC reality** — 影刀 log busy-check, GBK/UTF-8, Funnel/Tunnel, no inbound port.

**Do not try to beat in v1.6:** UiPath Studio, k8s autoscaling, multi-tenant SaaS billing, general computer-use.

## 5. v1.6 implementation directions (phased)

Priority is **product risk**, not “new runtime romance.” Each item names the module to change or marks **greenfield**.

### Wave 0 — P0 product foundation (stability people can trust)

Close the remaining V1.5 ops holes so the rest of v1.6 is not built on sand. Mostly existing files.

| # | Direction | Target | Done when |
| --- | --- | --- | --- |
| 0.1 | **ACCEPTED liveness** | `task/monitor.py` + `attempt.accepted_at` | ACCEPTED with no `task.running` for N seconds (default 60–120) → `task.accepted_stalled` event, then retry or FAILED — **not** wait 1800s |
| 0.2 | **DEVICE_BUSY clarity** | `dispatcher.py`, agent tools, Dashboard task row | One policy object: command vs capability must not silently disagree. Operator sees `{code: DEVICE_BUSY, blocking_task_id, queue_depth}` |
| 0.3 | **Dirty WS isolation** | `api/websocket.py` `_dispatch` | Event errors return `error` envelope; only auth/protocol kill the socket |
| 0.4 | **Server streaming uploads + size cap** | `api/artifact.py`, `api/capability.py`, `artifact/service.py` | Mirror client: `.part` + incremental hash; reject over cap; no `file.read()` of 658MB |
| 0.5 | **Fail-closed admin** | `auth/admin.py`, `main.py` lifespan | Non-loopback / non-local `SERVER_PUBLIC_URL` **refuses to start** without `AGENTHUB_ADMIN_TOKEN`; `scan`/`register-local` path allowlist |
| 0.6 | **Notification ≠ poll (finish the job)** | `agent/notify.py`, `task/events.py`, Dashboard | Terminal always recorded as an **Alert**; DingTalk is one sink. Workflow and API tasks included. Do not require LLM to still be running |
| 0.7 | **Heartbeat vs I/O (server side)** | same as 0.4; confirm client watchdogs stay on | 1GB upload to **server** does not stall event loop (extend `scripts/stress_bigfile.py`) |
| 0.8 | **Unstick CI** | `tests/agenthub/test_capability_acceptance.py` | `pytest tests` completes without `--ignore` |

**Out of Wave 0:** new process runtime, marketplace, multi-tenant SaaS.

### Wave 1 — P0/P1 product surfaces (the thing users touch)

| --- | --- | --- | --- |
| **Admin / tenant UX** | Replace “one shared token in localStorage” with login + roles: `admin`, `operator`, `author`, `device`. `users` table already exists (`db/models.py`) as a stub. | `auth/`, `static/index.html`, `users` | Partial (extend User) |
| **Device fleet** | List: online, last_seen, worker version, installed capabilities, live task, last error, labels (`excel`, `yingdao`, `gpu`). Actions: drain / revoke / message / copy enroll command. | `device/`, Dashboard 设备 tab | Labels = new column |
| **Capability catalog (marketplace-*ish*)** | CRUD is already in `api/capability.py`. v1.6 is the **UX + pin**: list published versions, upload ZIP, publish, deprecate, pin version per device, see who has which checksum. Not a public store, not billing. | `capability_runtime/`, new Dashboard tab **能力包** (today’s 能力 tab stays “device-reported commands” or is renamed) | UX greenfield |
| **Run history** | Unify Task + AgentRun + WorkflowRun into one operator timeline: who asked, which device, progress snapshot, artifacts, error tail. Deep link from DingTalk `task_id`. | `api/tasks.py`, `api/agent.py`, `api/workflows.py`, Dashboard 任务 | Query/view, not a new engine |
| **Alerts** | First-class `alerts` (or reuse `task_events` with a `severity` projection): ACCEPTED stalled, download stalled, DEVICE_BUSY, device offline, checksum mismatch, capability install fail. Sinks: Dashboard badge, DingTalk, optional webhook. | **greenfield** `server/app/alert/` (thin) on top of existing monitors | Yes, thin |

Workflow UI (list definitions, start run, step graph) is **P1** — APIs exist (`api/workflows.py`), Dashboard has zero coverage.

### Wave 2 — Supervised processes (one workstream, not the release)

**Problem:** `Task` is a **one-shot** with timeout_at. That matches 影刀 robots and Excel preprocess. It does not match:

- a Python script that should stay resident (watch a folder, keep a COM/Excel session, serve a local loop);
- the Worker process itself, which today dies when the console user logs out.

**Design principle:** do **not** overload `Task.status=RUNNING` for “this process should live for days.” That would break timeout, retry, and STALE reconcile.

**Proposed greenfield plane:** `server/app/process/` (name bikesheddable: Process / Service / Daemon) + `client/worker/process/`.

| Object | Meaning | Not |
| --- | --- | --- |
| `ProcessSpec` | capability name + version **or** declared local entry, restart policy, log policy, device | A TaskAttempt |
| `ProcessInstance` | desired=RUNNING\|STOPPED on a device | ACCEPTED queue item |
| Control messages | `process.start` / `process.stop` / `process.status` / `process.logs` on existing Envelope | New broker |
| Data | logs as Artifact **or** ring buffer uploaded on interval | WS log spam |

**Two sub-deliverables (keep them named separately in the backlog):**

1. **Worker-as-OS-service (P0 for “product”)** — ship `client/` as a Windows service / NSSM / login item. Heartbeat survives logout. This is packaging, not a new execution type. Highest leverage.
2. **Long-running capability process (P1)** — push a persistent Python (or Yingdao-unattended) spec to a designated PC; Dashboard: status, last N log lines, restart. Reuses Capability packages + designated Worker. **This is Part One of the original request, scoped correctly.**

Task engine stays the path for one-shot jobs. Workflow can later have a step type `wait_process_healthy` — **not** in v1.6 P0.

### Wave 3 — Security, packaging, observability, onboarding

| Theme | Direction | Module |
| --- | --- | --- |
| **Remote code** | Publish capability = privileged; zip-bomb limits; optional min-trust: only packages whose checksum is in `published`; never execute params as paths/URLs (already true for Python/HTTP) | `package_service.py`, `client/.../cache.py` |
| **Tenancy / auth** | Device-scoped artifact download (task.target_device_id); rate-limit registration; H5 confirm ACTION in production default | `api/artifact.py` M1, `security.py` M2, `config.py` |
| **Packaging** | `pyproject.toml` still says DeviceLink V1.0. v1.6: version the **product**; worker installer; `docker-compose.yml` today is **MySQL only** — add a documented server image *or* a single `scripts/dev_up.py` | `pyproject.toml`, `docker-compose.yml`, **greenfield** installer |
| **Observability** | Structured JSON logs with `task_id`/`attempt_id`/`device_id`; expose monitor counters (accepted_stalled, dispatch_cas_loss, download_stalled) on `/api/health` or `/api/metrics` | `main.py` logging, TaskMonitor |
| **First device in 10 minutes** | Wizard: (1) start server health, (2) create enroll code in Dashboard, (3) paste one command on the PC, (4) see device **online** + sample `echo` task. Collapse MySQL/Alembic/Funnel into a checklist with copy-paste, not a 400-line runbook as the only path | Dashboard + `docs/运行手册-V1.5.md` slim “Quickstart”; Worker installer |

**10-minute path (acceptance test, not a slogan):**

1. Operator opens Dashboard, logs in.
2. Clicks “添加设备”, gets `DL-XXXX-XXXX` + a single command line (installer or `python -m agenthub_worker --server … --code …`).
3. PC appears **online** with heartbeat.
4. Operator runs built-in `echo` (or `python.demo`) from the UI, sees SUCCESS + events without touching DingTalk or `agent_tools.json`.

If that still requires editing `capabilities.json` to match a command row, onboarding has failed.

## 6. Suggested sequencing (how the workstreams interlock)

```
Wave 0 reliability  ─────────────────────────────────────────────►
Wave 1 surfaces     ──────► fleet + run history + alerts ───────► catalog UX
Wave 2 processes        Worker-as-service ──► process plane (P1)
Wave 3 trust/onboard  fail-closed auth ──► ACL ──► 10-min enroll
```

**Dependency notes:**

- Alerts (Wave 1) want 0.1 ACCEPTED liveness and 0.2 DEVICE_BUSY codes, or the inbox will be empty/wrong.
- Catalog UX (Wave 1) can ship against **current** capability APIs; no process plane required.
- Process plane (Wave 2.2) should reuse Envelope + designated device + packages; do not invent a second dispatcher.
- 10-minute enroll (Wave 3) wants fail-closed auth (0.5) so the wizard is not an open relay.

## 7. Explicit non-goals (v1.6)

Say no in the PR description so scope cannot collapse back into “long-running Python.”

1. **Not** “AgentHub = a daemon that runs a Python script.” One-shot Task + Workflow + Yingdao remain the default execution path.
2. **Not** a public capability marketplace with payments, comments, or third-party signing CA. Versioning + pin is enough.
3. **Not** multi-region SaaS tenancy, org-switcher, or per-tenant databases. Roles on the existing `users` table is the ceiling.
4. **Not** Kubernetes workers, Ansible replacement, or inbound SSH to office PCs.
5. **Not** LLM computer-use driving 影刀/Excel click-by-click. Agent stays a planner.
6. **Not** replacing 影刀 / Excel / local Python as the actual work engines.
7. **Not** introducing Redis/MQ “because production.” V1.1 explicitly rejected that; monitors stay sweep + CAS unless a measured bottleneck appears.
8. **Not** rewriting Dashboard in React as a prerequisite. `index.html` can grow; a SPA is optional P2.
9. **Not** making CapabilityResolver smarter than “explicit > reporter > lazy-pull by load.” Fair scheduling / GPU binpack is out.
10. **Not** using the LLM tool loop as a job scheduler (V1.5 already burned `AGENT_MAX_TOOL_CALLS` on polls).

## 9. Success criteria for the v1.6 *release* (when we later implement)

A v1.6 implementation is done when **all** of these are true — not when a long-running Python demo exists.

1. An operator who did not write this repo enrolls a PC in **≤10 minutes** and runs `echo` from Dashboard.
2. ACCEPTED cannot sit unexplained past the liveness window; Dashboard shows stalled vs running vs queued.
3. DEVICE_BUSY is a visible, documented state with the blocking task id.
4. A 500MB artifact upload/download cannot OOM the server or freeze heartbeats.
5. Task success/fail produces an Alert (and DingTalk if configured) whether or not the Agent run is still open.
6. Capability versions can be published and pinned from the UI; devices report which checksum they run.
7. Worker survives Windows logout (OS service), with a documented restart.
8. Long-running process control exists **and** is documented as a separate plane from Task.
9. Admin token cannot fail open on a public URL; artifact download is device-scoped.
10. `pytest tests` is green without ignore flags.
