# AgentHub V1.6 产品路线图：Fleet Execution & Operationalization

> **状态：** 仅设计（本 PR 不含 Service 运行时代码）。
> **基线：** V1.5 Remote-Exec-1.0 + Lifecycle-1.0，git `main` @ `5022651`。
> **读者：** 决定「下一版做什么」的产品/运维，以及要把这些判断落到本仓库的工程师。

---

## 0. 一句话意图与非目标

**一句话：** V1.6 = **多设备执行与运行管理（Fleet Execution & Operationalization）**。V1.5 已经证明 Capability + Artifact 能在**指定办公 PC**上跑通；V1.6 要证明**多台真实办公 PC 能被当成可靠执行池来管理和调用**。

**北极星验收：** 操作员能把 ≥2 台已注册办公 PC 看成一个执行池：看见连通性与调度态、指定或解析到一台 READY 设备、派发一次 Capability Execution、在 Dashboard / 钉钉看到终态，且断线不会把写操作盲着重跑。

### 0.1 硬规则（不可破）

```
一次用户请求  →  一次 Capability Execution  →  一个 Task  →  一台 Worker
```

- **不要**引入 Job → N Tasks / MapReduce / 自动分片作为 V1.6 范围。
- **不要**把 Resolver 做成集群调度器（没有公平队列算法、没有副本替换、没有自动扩缩）。
- **不要**让 Agent tool-loop 当长驻 waiter / 调度器。
- V1.3 Workflow 已存在的「流程一步一 Task」保持原样，**本版不升级编排**；Fleet 工作只保证每一步仍然落到一台 Worker。

### 0.2 明确非目标（移到 V1.7+ 或本文件末尾「非目标」）

| 移出 V1.6 | 原因 |
| --- | --- |
| Job 抽象 / 自动 Task 扇出 / MapReduce | 违反硬规则；那是分布式计算产品，不是办公 PC 执行池 |
| SaaS 多租户、Billing、MSP 配额、计量即产品 | 上一版把「可售卖」误写成「先做商业化」 |
| Vault / IdP 作为 P0/P1 刚需 | 本版最多 P1 任务级密钥注入；Vault/IdP 是 P2 |
| 长驻 Process / Daemon 平面作为默认工作流 | Task 仍是一次性执行；常驻只作可选 P1 备注 |
| Kubernetes / Celery / Kafka「为了完整」 | 办公 NAT + GUI/影刀 会话，不是服务器 worker 集群 |
| 多 Agent 编排升级 | Reasoning 平面不是本版卖点 |
| 用 Agent tool-loop 当长任务等待器/调度器 | V1.5 已把 `wait=False` → CONFIGURED 定为正确方向 |

## 1. 对上一版「可售卖 SaaS 执行平面」框架的批评

上一版 `docs/v1.6-product-roadmap.md`（PR #1 初稿）把 V1.6 写成：

> 可注册、可调度、可观测、**以后可计费**的 Agent 执行平面……P1 就上租户 / 计量；产品化门槛是 30 分钟冒烟 + MSP 可转售。

这把三件不同的事捆在一起，导致范围膨胀：

1. **把运维问题写成商业化问题。** V1.5 的真实缺口是：设备只有 online/offline、DEVICE_BUSY 两条策略、ACCEPTED 可僵尸 1800s、能力广告无 TTL、通知绑在 AgentRun 上。这些是「多机能不能当池子用」，不是「能不能向 MSP 开票」。
2. **过早引入 Job。** 「fleet + job + package + artifact + alert」暗示一次请求可扇出多 Task。本仓库的可靠单元已经是 **Task + Attempt**（`task/state.py`、CAS 派发）。再套一层 Job，会和 V1.1 状态机抢权威。
3. **P1 塞进了不该在本版证明的东西。** 租户隔离、metering hook、队列 SLA 作为商业语言、Vault/IdP、process 平面——这些都不证明「第二台办公室电脑能不能被正确选中并跑完」。
4. **Persona 错位。** MSP/ISV、billable plane、50–500 机「可售卖」会把 Dashboard 做成假 SaaS 控制台，而不是最小 Fleet 操作台。

V1.6 修正为：**先把多台办公 PC 管成执行池。** 租户 / 计费 / Job 扇出 / 长驻进程，一律后移。下面 §2 是对着 `main@5022651` 的只读核对，后续章节只把这些缺口产品化，不借机加 Job/SaaS。

## 2. 本仓库现状审计（`main@5022651`，只读）

对照 git `5022651`。下列是 Fleet 产品化的地面事实，不是愿望清单。**仓库里没有 Job 表、没有 Task 扇出、没有 tenant/metering 模块**——不要为「完整」去发明它们。

### 2.1 Worker ≡ Device；两套能力广告

| 事实 | 路径 |
| --- | --- |
| Worker 不是独立进程身份。`TaskManager.worker_id` 在启动时赋值为 `identity.device_id` | `client/main.py`（`self.task_manager.worker_id = self.identity.device_id`） |
| **旧平面** `device_capabilities`：命令级广告（`command_name`/`version`/`enabled`），**无** `last_seen_at` | `server/app/capability/db_models.py`、`capability/service.py`；WS `device.capabilities` → `api/websocket.py` |
| **新平面** `worker_capabilities`：已安装能力包（`capability_name`/`version`/`status`/`last_seen_at`） | `capability_runtime/db_models.py`、`capability_runtime/worker_registry.py`；WS `worker.capabilities` → 同文件 `api/websocket.py` |
| `last_seen_at` **只写不失效**。`replace_worker_capabilities` / `mark_worker_status` 刷新时间戳；Resolver **从不**按 TTL 丢掉广告 | `worker_registry.py`；`capability_runtime/resolver.py` 只过滤 `Device.status == "online"` |
| `forget_worker()` 已实现，**全仓库零调用**（revoke 不清广告） | `worker_registry.py` 定义处；`device/service.py` `revoke_device` 只撤 token |
| Dashboard「能力」页、Agent `get_device_capabilities` 读的是**旧平面** | `static/index.html` → `/api/device-capabilities`；`agent/tools/device.py` → `CapabilityService.get_device_capabilities` |
| Capability 选机读的是**新平面** | `resolver.py` ← `WorkerCapability` |

V1.6 不合并两张表为新产品，但 P0 必须：广告 TTL、revoke 时 `forget_worker`、控制台/Agent 能看见 **worker_capabilities**（安装态），而不是只展示旧命令广告。

### 2.2 设备状态：只有 offline/online/revoked；在线口径不一致

`devices.status`（`db/models.py` Device）运行时只被写成 `offline` / `online` / `revoked`（`device/repository.py` `set_revoked` → `status="revoked"`）。**没有** `READY` / `BUSY` / `DRAINING` 列，也没有 labels/drain/preflight 模块。

| 谁在问「在不在线」 | 口径 | 路径 |
| --- | --- | --- |
| Dashboard / Device API | **Hub 连接数** `online = connection_count > 0`（DB status 是心跳宽限期滞后视图） | `device/service.py` `to_out` |
| Agent 设备工具 | **Hub** `hub.is_device_online` | `agent/tools/device.py` `_device_brief` |
| Capability Resolver | **DB** `Device.status == "online"` 且 `revoked_at IS NULL` | `capability_runtime/resolver.py` `_online_worker_ids` |
| 旧 Command 派发 | **Hub** `device_link.is_online` | `task/dispatcher.py` |

同一台机可以：Hub 已掉（API 显示离线），DB 仍 `online`（Resolver 仍选它）；或相反。V1.6 双轴状态必须先统一「活着 = Hub」，调度态另列，**不要**继续让 Resolver 读滞后 DB。

BUSY 今日也不是设备字段：Agent 用 LIVE+PENDING 任务集（`agent/tools/device.py` `BUSY_TASK_STATES`）；Dispatcher 用 `LIVE_TASK_STATES` 查 `tasks.target_device_id`。

### 2.3 ACCEPTED / 忙策略 / 看门狗

| 事实 | 路径 |
| --- | --- |
| Worker **先** `*.accept` **再** `_queue.put`；出队才 `*.running`。Accept ≠ 正在跑 | `client/worker/manager.py` `on_dispatch` / `_echo_type` |
| `attempt.accepted_at` 有写入 | `task/service.py` 处理 `task.accept` |
| **没有 ACCEPTED 活性扫描**。Monitor 对 SENT/ACCEPTED/RUNNING 只用 `timeout_at`；另给 SENT+设备掉线一条 600s。ACCEPTED 坐满能力默认 1800s | `task/monitor.py` `timeout_scan` |
| 旧 Command：设备 LIVE → 新任务 **FAILED `DEVICE_BUSY`** | `task/dispatcher.py` ~91–107 |
| Capability：设备 LIVE → 新任务 **回 PENDING**（Monitor 再扫） | `task/dispatcher.py` `_dispatch_capability` ~217–230 |
| Agent `execute_command`：忙则工具失败、不建任务 | `agent/tools/command.py` |

不存在 Job→N Tasks：`TaskService.create` 对 CAPABILITY 强制「恰好一步」（`task/service.py`）。Attempt 只是重试账本。

### 2.4 pin / risk_level / retryable

| 事实 | 路径 |
| --- | --- |
| 创建时钉 `capability_version`（`get_published_version` 写回 payload） | `task/service.py` |
| `package_id` / checksum **不落 Task 行**，只在派发信封里带出 | `task/db_models.py` 无 `package_id` 列；`task/dispatcher.py` envelope `package_id`/`checksum` |
| `risk_level` 在能力定义与 Agent 工具上存在 | `capability_runtime/db_models.py`、`agent/tools/base.py` |
| Dispatcher / Monitor / `request_retry` **不读** `risk_level` | `task/dispatcher.py`、`task/monitor.py` |
| Worker 失败可带 `retryable`（如 `EXECUTOR_BUSY`） | `client/worker/capability/result.py`、`executors.py` |
| 服务端 **忽略** `retryable`（全仓库 server 侧无消费） | 检索仅 `task/monitor.py` 注释里的英文单词 |

### 2.5 通知仍绑 AgentRun；`execute_command` 仍同步等 ~1900s

| 事实 | 路径 |
| --- | --- |
| 终态广播已有 | `task/events.py` `notify_task_terminal` |
| 钉钉投影：**仅当**存在 `AgentRun.task_id` **且**该 run 已 `SUCCESS/FAILED/CANCELLED` | `agent/notify.py` `_notify` |
| `run_capability` 默认 `wait=False` → `CONFIGURED`（正确方向） | `agent/tools/capability.py` |
| **`execute_command` 仍** `await _wait_terminal(..., settings.agent_tool_wait_max)`，默认 **1900s**，`waits_task=True` | `agent/tools/command.py`；`core/config.py` `AGENT_TOOL_WAIT_MAX` |

V1.6 不是升级多 Agent；P0 只要求终态走 Task 事件，并让命令路径停止把 tool-loop 当 1900s waiter（与 `run_capability` 对齐）。

### 2.6 Artifact ACL 与 SHA/IO

| 事实 | 路径 |
| --- | --- |
| 下载：任意有效设备 Bearer 即可下任意 `artifact_id`（校验 token，**不**校验是否本 Task 的 Worker） | `api/artifact.py` `download_artifact` |
| 服务端上传仍 `await file.read()` 整包进内存 | `api/artifact.py`；能力包同样 `api/capability.py` |
| 客户端下载：流式 + stall/total + cache SHA 走 `to_thread` | `client/worker/capability/downloader.py` |
| 拉包：流式分块后 **`b"".join(chunks)` 整 ZIP 回内存**，再 `to_thread(cache.install, ..., data)` | `client/worker/capability/puller.py` `download`；`capability/manager.py` |
| 其它 SHA/IO 已部分下环：copyfile、venv、uploader、影刀探测 | `manager.py`、`capability/executors.py`、`uploader.py`、`yingdao.py` |

### 2.7 已修好、不要回潮

`asyncio.shield(event.wait())` 导致的 Event.wait 泄漏（2026-09-15 52× pending destroy）已在 Phase 5 去掉 shield，并由测试钉死：**不要再当 P0 重开。**

- 回归：`tests/agenthub/test_phase5_event_lifecycle.py`（`test_wait_terminal_poll_loop_does_not_leak_waiter_tasks`）
- 实现：`agent/tools/task.py` `_wait_terminal`；`core/background.py` `spawn` 强引用

### 2.8 Fleet UI

`server/app/static/index.html`：设备/任务/命令/能力/数据源/Agent。任务详情 `openTask` 渲染 steps/attempts/events，**不读** `AttemptOut.progress`（API 已在 `api/tasks.py` `_task_detail` 填 `progress=a.progress_json`）。能力页打 `/api/device-capabilities` 而非 `/api/capabilities`。无双轴状态、无队列深度、无 pin checksum。

## 3. 核心模型

V1.5 四元模型继续有效，V1.6 只在其上加 **Fleet 运行态**：

| 概念 | 是什么 | 不是什么 |
| --- | --- | --- |
| **Capability** | 程序包（ZIP + manifest + 版本） | 不是设备广告（那是 `worker_capabilities`） |
| **Artifact** | 数据（输入/产物，HTTP 数据平面） | 不是任务结果 JSON |
| **Task** | **一次** Capability Execution | 不是 Job、不是 Map 任务集 |
| **Worker / Device** | 执行地点（一台命名办公 PC） | 不是连接、不是 k8s replica |
| **Fleet**（本版新增产品面） | 多台 Device 的注册、双轴状态、解析、排队、观测 | 不是集群、不是多租户组织树 |

地面事实见 §2。本节只定义 V1.6 **要变成什么样**。

### 3.1 Device / Fleet：双轴状态

连通性与调度资格必须拆开。今日 `devices.status` **只有** `offline`/`online`/`revoked`（`db/models.py`、`device/repository.py`），没有 READY/BUSY/DRAINING。更糟的是「在不在线」三条口径并存（§2.2）：API/`device/service.py` 与 `agent/tools/device.py` 用 Hub 连接数，`capability_runtime/resolver.py` 用 DB `status=="online"`。Worker 身份就是 Device（`client/main.py` `worker_id=device_id`），不要再造第二套 Worker 主键。

**轴 A · Connectivity（连通性）**

| 状态 | 含义 | 今日代码 |
| --- | --- | --- |
| `ONLINE` | Hub 上至少一条活连接 + 业务心跳未过宽限期 | `websocket/hub.py` 连接数；心跳 15s / 离线 45s（`client/heartbeat.py`、`websocket/heartbeat.py`） |
| `OFFLINE` | 无活连接，或超过宽限期 | HeartbeatMonitor 写 `devices.status=offline` |

**轴 B · Scheduling（调度资格）**

| 状态 | 含义 | 今日代码 |
| --- | --- | --- |
| `READY` | 可接新 Task | **不存在**。目前用「无 LIVE 任务」近似 |
| `BUSY` | 已有 LIVE Task（`max_concurrency=1`，GUI/影刀正确） | LIVE 查询散落在 `task/dispatcher.py` |
| `DRAINING` | 不再接新 Task，在途跑完或取消后再撤销 | **不存在**（只有 `POST /api/devices/{id}/revoke`） |

**身份生命周期（与双轴正交）**

| 状态 | 含义 | 今日代码 |
| --- | --- | --- |
| `REGISTERED` | 注册码换到 `device_id` + token | `registration/service.py`、`api/devices.py` |
| `REVOKED` | token 失效，WS 4403，客户端停止重连 | `devices.revoked_at`、`api/devices.py` |

**产品铁律：** WS 断开 ≠ 设备终态，更 ≠ 任务终态。执行绑定 Worker **进程**（`client/worker/manager.py` 头注：RPA lifetime bound to process, not WS）。Ledger（`client/worker/ledger.py`）重连补报结果，不重跑。

### 3.2 Task / Attempt

沿用 V1.1 双状态机（`task/state.py`）：

```
Task:    PENDING → DISPATCHING → SENT → ACCEPTED → RUNNING → 终态
Attempt: 每次派发一行；current_attempt_id 是事件门；迟到结果只审计
终态:    SUCCESS / FAILED / TIMEOUT / CANCELLED（不可逆）
```

V1.6 必须产品化、今日尚未做的三点：

1. **Accept ≠ Running。** Worker 入队即报 `*.accept`，出队执行才报 `*.running`（`client/worker/manager.py` `_echo_type`）。服务端 ACCEPTED 不能当成「已经在跑」。
2. **ACCEPTED 活性。** `attempt.accepted_at` 已写入（`task/service.py`），**从未被 Monitor 使用**。SENT 掉线有 600s（`task/monitor.py`）；ACCEPTED 一直等到 `timeout_at`（能力默认 1800s）→ 审计 H3 / 地平线1号僵尸。
3. **一个 Task 只对应一台 Worker。** `tasks.target_device_id` 在 capability 派发时落盘（`dispatcher._dispatch_capability`）。禁止运行中换机；重试是否换机由 `risk_level` 决定（见 3.7），默认写操作不换机盲派。

Attempt 是重试账本，**不是** Job 的子任务。`request_retry` 开新 Attempt，不改写旧行。

### 3.3 Capability pin（版本 + checksum）

| 层 | 今日 | V1.6 要求 |
| --- | --- | --- |
| 定义 | `(name, version)` 唯一、不可变（`capability_runtime/service.py`） | 保持 |
| Task 记录 | `tasks.capability_name` + `capability_version`（创建时 `get_published_version` 钉死，`task/service.py`） | **同时落** `package_id` + checksum；禁止只在 WS 信封上出现（今日 `dispatcher.py` 派发才带 `package_id`，Task 行无此列） |
| 包校验 | 信封已带 `package_id` + `checksum`（`dispatcher.py`） | Resolver / Preflight / Dashboard 都展示并校验同一 checksum |
| 设备广告 | `worker_capabilities.last_seen_at` 有列 | Resolver **必须 TTL**；过期广告不能当 READY |

`CapabilityResolver.resolve_worker` 今日在无显式设备时，会 fallback 到**任意在线 Worker 做 Lazy Pull**（`resolver.py` 注释 §52）。V1.6 收紧：未匹配能力且未声明可拉包的设备，**不能**被静默选中。Lazy Pull 仍允许，但必须是「该设备广告过该能力、或操作员显式点名」之后的安装步骤，而不是调度策略。

### 3.4 Artifact 数据平面

V1.5 铁律不变：**WS 只传控制与引用，字节走 HTTP。**

V1.6 要把数据平面做成 Fleet 可用，而不是单机碰巧能跑：

| 项 | 今日 | V1.6 |
| --- | --- | --- |
| 设备 ACL | 任意有效设备 Token 可下任意 blob（`api/artifact.py` download，审计 M1） | 仅 `target_device_id`（或该 Task 的 Worker）+ Admin |
| 流式进度 | Worker 有 progress；服务端上传仍 `await file.read()`（H2） | 服务端流式；Dashboard 看得见 stall vs 传输中 |
| 超时三维 | 客户端已有 connect/read、stall 90s、total 900s（`client/worker/capability/downloader.py`） | 产品文案与错误码区分 **connect / stall / total**；禁止混成一个 TIMEOUT |
| 心跳隔离 | 客户端 SHA/落盘已 `to_thread` | **禁止**用 SHA / 磁盘 IO 堵住 WS 心跳循环（服务端上传路径仍违规） |

### 3.5 Device Resolver（设备解析器，不是集群调度器）

确定性顺序，禁止「智能调度」：

```
1. 显式 device_id（用户/Agent/API 点名）——仍须 ONLINE 且非 REVOKED
2. labels / pool 交集（P1；P0 跳过本步）
3. 能力匹配（worker_capabilities 钉住的 name+version，且广告未过 TTL）
4. 调度态 READY（非 BUSY / 非 DRAINING）
5. 负载（现有 `_order_by_load`：LIVE Task 数升序，再 worker_id）
```

这是 **解析**，不是调度集群：没有抢占、没有把 BUSY 机上的 GUI 会话杀掉换机、没有自动把一个 Task 拆到多机。

今日实现：`server/app/capability_runtime/resolver.py`。显式设备已优先；缺 labels、缺 READY、缺广告 TTL、有「任意在线兜底」。

### 3.6 Preflight（派发前）

在 CAS 抢单并 `task.dispatch` / `capability.execute` 出站之前，必须有一次只读预检。失败则 **不创建 Attempt**（或创建后立即 FAILED 且 error_code 可操作），避免「派出去再发现没包 / 没盘 / 设备在抽水」。

P0 预检清单：

- 设备 `ONLINE` ∧ 调度 `READY` ∧ 非 `REVOKED`
- 钉住的 capability version 已 PUBLISHED，checksum 已知
- 能力广告未过 TTL（或显式点名 + 允许 Lazy Pull）
- 输入 Artifact 行存在（今日 dispatcher 已查 `ArtifactService.get_artifact`，可升格为 Preflight 步骤）
- 目标设备对输入 Artifact 有 ACL 资格

P1 再加：磁盘/环境清单、安装态、本地 cache 命中预测。

落点：新模块或 `task/dispatcher.py` 内明确的 `_preflight()`，不要散落在 resolver / busy 锁 / artifact 查找三处 silently。

### 3.7 Retry 与 `risk_level`

`risk_level ∈ {READ, WRITE, ACTION}` 已在能力定义上（`capability_runtime/db_models.py`、`CapabilityService.RISK_LEVELS`），Agent 工具也有（`agent/tools/base.py`）。**Dispatcher / Monitor / `request_retry` 不读它。** Worker 失败载荷里的 `retryable`（`client/worker/capability/result.py`，如 `EXECUTOR_BUSY`）服务端同样忽略。

| risk_level | 自动重派 | 典型 |
| --- | --- | --- |
| `READ` | 允许：checksum mismatch（可重下）、download stall、SENT 未接受就掉线 | Excel 预处理只读、下载 |
| `WRITE` / `ACTION` | **禁止盲着重派**。WS 闪断、ACCEPTED 僵尸、进程还在 → 等 Ledger 补报或人工 `request_retry` | 影刀（`client/worker/executors/yingdao.py`） |

`retryable=true` **不能**压过 WRITE/ACTION。机制已经具备：CAS、`task.late_result`、STALE、Ledger `attempt_id` UNIQUE。V1.6 只是把**产品策略**接到 Monitor / Dispatcher。

### 3.8 Notification（与 Agent 轮询解耦）

正确因果：

```
Task 终态  →  task/events.notify_task_terminal
                ├─ Dashboard（系统记录）
                └─ 钉钉 sink（操作员）
Agent 只是一种 intake；AgentRun 结束与否不决定「要不要通知」。
```

今日 `agent/notify.py`：**仅当存在 AgentRun 且该 run 已结束**才推送。API / Workflow / Dashboard 发起的任务，群里与操作台都可能静默。与此同时 `execute_command` 仍 `await _wait_terminal` 默认 1900s（`agent/tools/command.py`、`core/config.py` `AGENT_TOOL_WAIT_MAX`），而 `run_capability` 已默认 `wait=False`。V1.6：每个终态 Task 都是事件；钉钉是 sink；Dashboard 是事实源；命令路径对齐异步发起，**不**把 tool-loop 当 waiter。

### 3.9 Dashboard 与 RBAC

最小 Fleet Console（`server/app/static/index.html`），不是 SaaS 控制台：

- 设备：双轴状态、Hub 在线（与 Resolver 同口径）、labels（P1）、drain（P1）、revoke（revoke 时调用 `forget_worker`）
- 任务：队列（轻量 PENDING）、ACCEPTED vs RUNNING、**progress**（API `AttemptOut.progress` 已有，`openTask` 模态未画）
- 运行史：谁 / 哪台机器 / 哪个包版本（需 Task 行有 `package_id`）
- 能力目录：读 `/api/capabilities` + worker 安装广告；**不要**继续只打 `/api/device-capabilities`

RBAC 三角色，**单租户**：

| 角色 | 能做 |
| --- | --- |
| `admin` | 注册码、撤销、发布能力、改 RBAC、看全部 |
| `operator` | 派发/取消/重试、drain、看 Fleet |
| `viewer` | 只读设备/任务/产物元数据 |

今日：一个共享 `X-Admin-Token`；空 token = 全开放（`auth/admin.py`，审计 H1）。P0 必须 fail-closed。这不是多租户 SaaS。

## 4. 完整执行链（V1.6）

```
[Intake] 钉钉 / Dashboard / POST /api/agent/message / POST /api/tasks
    │  一次用户请求 → 选定一个 Capability（+ 可选显式 device / 可选 labels）
    ▼
[Pin]  CapabilityService.get_published_version(name, version)
    │  把 name + version + package checksum 写入 Task（不可在派发时漂移）
    ▼
[Create Task]  TaskService.create
    │  一个 Task、一个目标 Worker（或「待解析」但最终仍是一台）
    │  artifact_ids 只存引用
    ▼
[Light queue]  若目标 BUSY → 统一 DEVICE_BUSY 策略：进入 PENDING 等待（有界），
    │  不把新 Task FAILED 掉（与今日 command 路径相反）；也不扇出到第二台
    ▼
[Resolver]  显式设备 > labels/pool > 能力匹配 > READY > load
    ▼
[Preflight]  ONLINE+READY、广告 TTL、包 checksum、Artifact 存在与 ACL
    ▼
[CAS dispatch]  TaskDispatcher 条件 UPDATE PENDING→DISPATCHING（已有）
    │  出站 capability.execute（WS 控制面）
    ▼
[Worker]  accept（入队）≠ running（出队执行）
    │  HTTP 拉包 / 拉 Artifact（stall vs connect vs total）
    │  执行 → 上传产物引用 → task.result
    │  进程绑定；WS 断开由 Ledger 补报
    ▼
[Terminal]  notify_task_terminal → Dashboard + 钉钉
    │  READ 失败可按策略自动新 Attempt；WRITE/ACTION 停，等人
    ▼
[Audit]  task_events + attempt.device_id + capability_version + checksum
```

对照 V1.5 已通的单机链（`docs/V1.5_EXECUTION_LIFECYCLE.md`、`scripts/e2e_v15.py`）：本图多出来的只有 **Fleet 状态、统一排队、Resolver 收紧、Preflight、pin/TTL、通知解耦、RBAC/控制台**。没有 Job 层，没有第二套 dispatcher。

## 8. 相对 V1.7 的边界

V1.6 结束的标志是：**执行池可用**。V1.7 才讨论「执行池之上的产品形态」。

| 主题 | V1.6 | V1.7+ |
| --- | --- | --- |
| 执行粒度 | 1 请求 = 1 Task = 1 Worker | 才允许讨论 Job / 扇出 / 跨机流水线升级 |
| 租户 | 单组织 + RBAC | 多租户行隔离、MSP |
| 密钥 | 任务级 handle | Vault / IdP |
| 进程 | Task 一次性；Service 包装可选 | Process 平面（若仍需要） |
| 编排 | 不改 V1.3 Workflow / V1.2 Agent | 多 Agent、更复杂编排 |
| 发布 | pin + 人工选版本 | canary / 分批 |

若某一需求必须破坏「一请求一 Task 一 Worker」，它**默认不属于 V1.6**，应单开 V1.7 设计，而不是塞进 Fleet 里程碑。

## 9. 可选 P1：长驻 Python / Worker 服务（按比例）

`Task` 带 `timeout_at`，适合影刀与 Excel 预处理。**不要**用 `Task.status=RUNNING` 表示一个活了几天的进程。

本版标题仍是 Fleet Execution。与「机器一直活着」相关的只有两件，且都是 P1、可砍：

1. **Worker 作为 Windows Service（优先）**  
   解决「注销后 `python client/main.py` 死了，池子里的机器假死」。这是包装（NSSM / WinSW / 服务安装脚本），不是新执行模型。落点设想：`client/packaging/`。

2. **长驻能力进程（更可砍）**  
   若必须推一个常驻脚本：独立 `ProcessSpec/Instance`，复用 Envelope 与指定 Worker，**另开平面**。不得吃掉 P0 工期，不得引入 k8s 式副本。

Agent **不得**用 tool-loop 睡眠等待该进程。
