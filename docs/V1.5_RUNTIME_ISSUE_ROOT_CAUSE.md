## 1. 当前状态模型（审计基线）

### 1.1 服务端 Task 状态机（task/state.py:20-33）

```
PENDING →(dispatcher CAS)→ DISPATCHING →(发送成功)→ SENT →(task.accept)→ ACCEPTED
        →(task.running / 多步推进)→ RUNNING → SUCCESS / FAILED / CANCELLED
PENDING --600s(offline)--> TIMEOUT          (monitor.dispatch_pending, monitor.py:55-61)
SENT/ACCEPTED/RUNNING --timeout_at--> TIMEOUT (monitor.timeout_scan, monitor.py:73-86)
任意非终态 →(request_cancel 同步直改)→ CANCELLED (service.py:475-484)
DISPATCHING →(server 重启恢复)→ PENDING      (monitor.py:115-141)
```

attempt 另有 STALE 态（state.py:38-48），但**没有任何清扫路径会产生它**。

### 1.2 Worker 内部状态（worker/manager.py）

```
收到 dispatch → 写 _active + 上报 accept（manager.py:273-276）→ 入 _queue（:278）
消费者单协程串行取队列（:297-309）→ state.status="queued"→"running"→ 终态上报
```

**关键语义缺陷：worker 的 accept 上报发生在"进入执行队列之前"（:273-278），且队列中未开始的任务也在 `_active` 里** —— 服务端 ACCEPTED ≠ 开始执行，甚至 ≠ 排到队首。

## 2. 问题逐项审计

### 问题 1：Task 配置成功后没有通知用户

**当前行为**：用户经钉钉发起 `run_capability`，从创建到收到第一条回复要等 agent 整个 run 结束（含最长 1900s 的同步等待）。

**调用链**：钉钉消息 → AgentService.handle_message（service.py:63）→ create_task 后台 run（service.py:96-98，**引用未保存**）→ 工具 run_capability（tools/capability.py:103-166）内部同步 `_wait_terminal(1900s)` → run finalize 时才 `_send` 回钉钉（service.py:250-268）。PENDING→SENT 之间无任何用户通知钩子（审计确认 server 全库无此钩子）。

**根因**：通知与 run 生命周期耦合——"任务已配置"这个事实没有独立的通知出口。

**修改点（Phase 3/4）**：run_capability 创建任务成功后立即返回 `CONFIGURED`（含 task_id），由 agent 回复"任务已配置"；终态通知由问题 3 的通知层承担。

### 问题 2：Worker 忙线/僵尸时新 Task 永久卡 ACCEPTED

**当前行为**（生产实测）：地平线1号上一个任务停等在半死下载上，新任务 17:45:15 派发后被 accept，此后永久 ACCEPTED；服务端 cancel 改了状态，worker 侧停等协程不受影响。

**真实调用链**：
1. `on_capability_execute`：写 `_active` → 上报 accept → `queue.put`（manager.py:273-278）。accept 先于执行。
2. 单消费者 `_consumer_loop`（manager.py:297-309）串行执行；上一个 attempt 卡死 → 队列无限堆积（`asyncio.Queue()` 无界，:85）。
3. 卡死点在 `_prepare_inputs → ArtifactDownloader.download`（manager.py:491 → downloader.py:71-111）：GET 200 后 body 龟速滴漏，httpx `timeout=300` 是**分阶段超时**（相邻两次 socket 读的间隔），滴漏时永不触发（downloader.py:27,102）。
4. `on_cancel`（manager.py:280-293）只做 `cancel_event.set()`，**从不 task.cancel()，且无任何代码持有下载协程引用**；`_fetch` 全程不检查 cancel Event；唯一检查点在多 artifact 之间（manager.py:482）→ 停等中的下载对取消免疫。
5. 服务端兜底只有整段超时：ACCEPTED 无活性探测，`timeout_scan` 要等满 `timeout_at`（CAPABILITY 默认 1800s，config.py:110）；`offline max wait 600s` 只作用于 PENDING（monitor.py:55-61）。服务端 cancel 是"登记式"：`request_cancel` 先同步置 CANCELLED（service.py:475-484）再 fire-and-forget 广播（api/tasks.py:136-138），投递失败（hub.py:81-94 返回 0）无人知晓，attempt 永久滞留。
6. 无 stale 检测：task 已终态但 attempt 仍 RUNNING、OS 进程已死但 ledger 仍 RUNNING、worker 重启只处理自己 ledger 里的 orphan（manager.py:91-93），两端都没有对账。

**根因**：三层叠加——worker accept 语义失真（accept≠入队执行）；下载协程无 cancel/超时通道；服务端对"非 RUNNING 的非终态"无活性探测、对"终态任务的非终态 attempt"无对账清扫。

**修改点（Phase 2 + Phase 6 联动）**：
- Worker：accept 改为"已入队"语义或在 running 时再上报；消费者对 cancel 状态的队首任务直接跳过（manager.py:299-306 现在不检查 cancel 就执行）；`_prepare_inputs`/download 传入 cancel Event（Phase 6 实现）；stale 检测：消费者开始执行前校验 `_active` 中前序 attempt 是否真终态。
- Server：TaskMonitor 增加 ACCEPTED 活性探测（accepted 后 N 秒无 running → 重派或失败）；任务终态后残留非终态 attempt 的对账清扫（补 STALE 态的生成路径）；cancel 投递失败（0 连接/发送异常）记日志并升级。
- `monitor.py:60` 用 `created_at` 判 PENDING 超时 → retry 的老任务会立即超时，改为按本次入 PENDING 时间。

### 问题 3：Task 运行结束没有主动通知用户

**当前行为**：agent run（含等待）结束早于任务终态时（1900s 等待上限），任务真正完成/失败时用户在群里收不到任何消息（东方神舟 16:43 SUCCESS，17:09 用户来问才知道）。

**调用链**：任务终态落库 → `TaskWaiters.notify`（task/waiters.py:38-47）+ `notify_task_terminal` 广播（task/service.py:449-453、task/events.py:33）→ **唯一订阅者是 workflow runtime**（main.py:97）。agent 侧：run 结束即 `_finalize`+`_send`，之后与任务断联。

**关键既有设施（复用而非新建）**：
- `AgentRun.task_id` 列已存在（agent/db_models.py:39），`AgentRunService.set_task` 已实现（agent/runs.py:87-91）——**全库无调用方**。
- `agent_runs.reply_webhook`（钉钉 sessionWebhook）已持久化（db_models.py:42），`_send` 可从 DB 重读（service.py:256-260）。
- `subscribe_task_terminal` 订阅机制现成（task/events.py:33）。

**根因**：Task→AgentRun→Channel 关联断裂（字段在、没人连），终态广播无人消费。

**修改点（Phase 3）**：
1. run_capability 创建任务后调 `AgentRunService.set_task(run_id, task_id)`（需要把 run_id 注入工具上下文——handler 签名 `(db, args)` 不含 run，用 contextvar/闭包注入）。
2. main.py 注册 agent 终态订阅者：task_id → AgentRun → reply_webhook → DingTalkSender，发送"任务已完成/失败/超时/取消 + artifacts 列表"。
3. 幂等去重：dedupe key = `task_id + event_type + attempt_id`（复用 TaskEvent 行），SUCCESS 只发一次。
4. sessionWebhook 是短期凭证：过期/失败容错（记日志，不抛）。

### 问题 4：中台进度落后于子电脑实际进度

**当前行为**：子电脑已执行到 C 步骤，中台仍显示 B。

**真实调用链（两层落后）**：
- **Worker 层丢失**：`progress` 闭包与 accept/running 直走 `_report`（manager.py:315-320,274,322），失败仅 stderr 打印（manager.py:545-547），**不入 ledger、不重发**；WS 断连窗口内的进度全部丢失（result 有 pending-reports 保障，progress 没有）。
- **Server 层无序**：`task.progress` 仅写一条 TaskEvent（service.py:374-381），不更新任何状态字段，**无 sequence/单调性防护**（task/ 全目录 grep sequence 零命中），旧进度可晚于新进度入库；事件循环阻塞（问题 8）还会延迟 worker 发送。

**根因**：进度是"尽力而为的通知"，不是"有保障的状态"。

**修改点（Phase 8 + Phase 7 联动）**：
- Worker：进度事件带单调 `seq`（per attempt）；发送失败时 ledger 记录"最后未送达进度"（至少保留最新一条，恢复后补发最新即可，不必全量）。
- Server：TaskEvent 增加 seq 字段（migration），按 attempt 单调处理——`seq <= 已存最大 seq` 的事件只入审计不覆盖展示态；attempt 表增加 latest_progress 冗余列（或复用现有字段），中台/agent 读 latest_progress 即不会落后或回退。

### 问题 5：AGENT_MAX_TOOL_CALLS=9 太小（架构问题）

**当前行为**：agent 为等长任务轮询 `get_task_detail`，17:09 的下载请求烧了 6 次调用后撞 9 次上限，`save_artifact` 没执行，任务结果拿不到。

**调用链**：run_capability（waits_task=True）同步阻塞 `_wait_terminal(1900s)` → 返回后 agent 还要再调 get_task_detail/save_artifact → `policies.py:219-223` 拒绝（MAX_CALLS_EXCEEDED）→ `nodes.py:151-158` decision=finish + error=AGENT_MAX_TOOL_CALLS → 模板回复"请把需求拆小一点"（nodes.py:192-195）。默认值 8（config.py:81），生产 9 为环境变量注入。

**根因**："长时间任务等待"被放进 LLM Tool Loop 的预算体系。等待重基（nodes.py:115-120 rebase started_at）只解决了 RUNTIME 预算，没解决 TOOL_CALLS 预算。

**修改点（Phase 4，遵循"run_capability 默认异步"）**：
1. run_capability 改为：创建任务 + dispatch → 立即返回 `{task_id, status:"CONFIGURED", note:"完成后将主动通知"}`，`waits_task=False`（tools/capability.py:146-166,195）。
2. 同步等待模式保留为显式选项（manifest/wait_policy 或 args.wait=True，供短任务），默认异步。
3. 任务结果（含 artifacts）由问题 3 的通知层推送；用户追问时 agent 用 get_task_detail 查询。
4. save_artifact 不依赖 run 上下文（tools/artifact.py:31-49），且 task.success 后 artifact_ids 已回填 Task 行（task/service.py:404-412），通知里可直接携带 artifact_id 供后续下载。

### 问题 6：Event.wait 泄漏（52 条 "Task was destroyed but it is pending"）

**根因（已定位到行）**：`agent/tools/task.py:109-111`：

```python
await asyncio.wait_for(asyncio.shield(event.wait()), timeout=agent_poll_interval*5)
```

`asyncio.shield` 的语义是**外层 wait_for 超时只取消 shield 外壳，内层 `event.wait()` Task 留在 pending**。轮询周期 10s（agent_poll_interval=2×5，config.py:66）→ 每 10 秒泄漏一个 pending Task；1900s 的等待积累约 190 个。事件最终 set 时它们会正常完成（无告警）；**只有事件永远不 set 的等待（deadline 1900s 返回、或 run Task 被 GC）会让 event↔future↔task 成环，被一次 GC 集中回收** → 生产 17:10:29 一瞬间 52 条 ERROR。同病：`agent/tools/workflow.py:72-78`、`agent/mvp/graph.py:214`。

加重因素：`asyncio.create_task` 返回值未保存（agent/service.py:96-98,130,164；api/tasks.py:84,138,149 等）——CPython 对 Task 仅持弱引用，run Task 可能被 GC，内部 waiter 连带销毁。

**修改点（Phase 5）**：
1. 轮询等待去掉 shield：`wait_for(event.wait(), timeout=...)`（超时会取消 waiter 本身，语义正确且无泄漏），或改用 `asyncio.timeout` 上下文。
2. `finally` 中 unregister（保留）+ 显式取消本地 waiter 引用。
3. fire-and-forget create_task 统一保存引用到集合 + done callback 移除（防 GC + 可观测）。

### 问题 7：大文件下载看门狗缺失（P0）

**当前行为**（生产实测）：GET 200 后 body 滴漏，无错误、无日志、无限等待；cancel 无效；单消费者被堵死。

**调用链与根因**：`ArtifactDownloader.download`（downloader.py:71-111）：
- `timeout=300` 分阶段超时，read timeout 只约束相邻两次读的间隔 → 滴漏连接永不触发（"transport alive, application dead"）。
- 无总时长上限、无 stall 检测、无 cancel 参数。
- `response.content` 全量进内存（:102）；`sha256_bytes(data)` 在事件循环上跑且 **f-string 里对同一数据算了第二遍**（:84,87）；`tmp.write_bytes(data)` 全量同步落盘（:92）。

同病：`puller.py:51-55`（包下载全量内存 + 双重哈希）；`uploader.py`（`UPLOAD_TIMEOUT=120` 同为分阶段超时，慢速滴漏上传可无限存活）。

**成功判定缺陷**：当前"200 OK = 成功"；应为 200 + 完整 body + checksum 一致（server 已下发 checksum，dispatch 携带）。

**修改点（Phase 6）**：
1. 流式下载：`client.stream()` 逐 chunk（如 1MB）读取，每 chunk 更新 `last_progress_at`；`now - last_progress_at > DOWNLOAD_STALL_TIMEOUT`（默认 60s）→ 关连接、清 .part 临时文件、抛 `ARTIFACT_DOWNLOAD_STALLED`。
2. 总时长 `DOWNLOAD_TOTAL_TIMEOUT`（默认 900s）兜底。
3. 每个 chunk 间检查 cancel Event（Phase 2 的取消通道打通点）。
4. 哈希流式增量计算（读 chunk 时顺手更新 hasher，替代全量二次哈希）；最终 checksum 校验在 to_thread。
5. uploader/puller 同等处理（上传：分块读文件 + stall/total 超时；拉包：同下载）。

### 问题 8：事件循环被大文件 IO 阻塞（含心跳独立性）

**当前行为**（生产实测）：地平线1号 16:51 `keepalive ping timeout → 1011` 断连，恰在输入下载阶段。

**根因（事件循环上的同步重 IO 全清单，逐行）**：

| 位置 | 调用 | 量级 |
|---|---|---|
| downloader.py:76 | `sha256_file(cached)`（cache-hit 路径） | 整个文件（数百 MB）逐 1MB 同步读+哈希 |
| downloader.py:84,87 | `sha256_bytes(data)`（**算了 2 遍**，87 在 f-string 里） | 整个响应体 |
| downloader.py:92 | `tmp.write_bytes(data)` | 全量同步写盘 |
| puller.py:52,55 | `hashlib.sha256(data)`（同样 2 遍） | 整包 |
| uploader.py:60-66 | 同步 file object 交 httpx multipart，分块同步 read 在 loop 上 | 整个文件 |
| executors.py:137-140,212-214,223-224 | context/params/stdout/stderr 同步写盘 | 子进程全部输出 |
| executors.py:177 | `subprocess.Popen` 在 loop 上 | Windows CreateProcess 数十~数百 ms |
| executors.py:244→388-409 | `sorted(base.rglob("*"))` 同步递归 | 整个输出目录 |

（对比：`copyfile` 已 `to_thread`（manager.py:500）；yingdao 执行器是健康范式——等待在 async 轮询里、阻塞调用全 `to_thread`（yingdao.py:103,130-132,144,193-215）。）

**心跳机制**：websockets 库内置 ping（ping_interval=20/ping_timeout=10，websocket.py:31-33）+ 业务心跳（15s，heartbeat.py:31-47）都是独立协程，与 app 层 send 共享同一 transport 但锁隔离——**1011 的真正机制是上述同步 IO 把整个事件循环卡住，心跳协程无法调度**，不是发送竞争。`websocket.py:54-58` send 无应用层锁（库内写锁保证帧原子，多协程写顺序不确定，可接受）。

**修改点（Phase 7）**：按"控制面 async / 数据面线程"原则，上表逐项移入 `asyncio.to_thread`（sha256 增量化后并入 Phase 6 的分块读）；`Popen`、rglob、stdout/stderr 落盘同移；上传改异步分块读。验收 = 1GB 传输全程 ping 不丢（Case 11）。
