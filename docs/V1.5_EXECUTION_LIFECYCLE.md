# V1.5 执行生命周期（修复后）

> Phase 1-10 修复后的四条生命周期与总架构图。根因见 `V1.5_RUNTIME_ISSUE_ROOT_CAUSE.md`，逐项修改见 `V1.5_RUNTIME_FIX_REPORT.md`。

## 1. Task 生命周期（服务端视角）

```
PENDING ──(dispatcher CAS)──> DISPATCHING ──(send ok)──> SENT ──(task.accept)──> ACCEPTED
   │                              │                        │                        │
   │ offline>600s                 │ send失败→回PENDING      │ 设备掉线>600s           │ worker开始执行
   │ (pending_since)              │ (重置pending_since)     │ → TIMEOUT(可重试)       ↓
   ↓                              ↓                        │                      RUNNING
TIMEOUT(可重试)            （对账：STALE）                    │                        │
                                                            └──────> 终态: SUCCESS / FAILED / TIMEOUT / CANCELLED
活性保障（Phase 2）：
- watchdog: timeout_at 到点 → TIMEOUT + 对 worker 的停止指令
- reconcile 扫描: 终态任务下仍存活的 attempt → 窗口内重投停止指令(去重) → 窗口后 STALE
- 每个非终态都有：进入条件 / 推进条件 / 超时条件 / 退出条件
```

## 2. Worker 内部生命周期

```
收到 dispatch(capability.execute)
  → [上报 accept]（语义 = 已接收，≠ 正在执行）
  → 进入单消费者队列（可被 cancel 就地取消：直接记 CANCELLED 上报，绝不执行）
  → 出队 → [上报 running]（executor 真正启动）
  → _prepare_inputs：逐 artifact 下载
       · 流式 1MB 分块 + 增量 sha256 + .part 原子落盘
       · 三重围栏：httpx 分阶段超时 / stall 90s / total 900s
       · cancel 事件与 chunk 竞速 → 取消立即生效（不再免疫）
  → executor.execute（Popen 在线程；stdout/stderr 落盘在线程）
  → 上传 artifacts（同步 httpx 在线程 + 总预算）
  → [上报 result]（send 失败入 ledger，重连自动补报）
恢复：worker 重启 → 孤儿 attempt 记 WORKER_RESTARTED 上报；服务端重启 → DISPATCHING 回 PENDING。
```

## 3. Artifact 传输生命周期

```
上传(Worker→Server): to_thread(同步 httpx) ──fence──> 总预算 900s（DEVICELINK_UL_TOTAL）
下载(Server→Worker): client.stream 1MB 分块
  每块三选一竞速: chunk 到达 / cancel 置位 / 超时(=min(stall, 剩余总预算))
  ├─ chunk ──> 增量 sha256 + .part 追加 ──> 循环
  ├─ cancel ──> ArtifactDownloadCancelled（任务随之 CANCELLED）
  ├─ 超时=stall 剩余 ──> ArtifactDownloadStalled（90s 无块）
  └─ 超时=总预算剩余 ──> ArtifactDownloadTimeout（900s 总账，跨重试连续）
成功 = 200 + 完整 body + sha256 一致（缓存命中也必须校验一致）。
```

## 4. 用户通知生命周期

```
用户消息 ──> AgentRun 创建(RUNNING) ──> run_capability
  ├─ Task 创建+派发成功 ──> set_task(run_id, task_id) 打通关联
  │     └─ 立即返回 CONFIGURED ──> agent 回复「任务已配置，完成后主动通知」
  ├─ wait=true（显式）──> 同步等终态（agent 自己带结果，通知层静默）
  └─ run 结束（成功/失败/放弃等待）……

Task 终态(SUCCESS/FAILED/TIMEOUT/CANCELLED)
  ──> notify_task_terminal 广播
       ├─ workflow runtime（既有）
       └─ agent 通知层（Phase 3）：反查 AgentRun
            ├─ run 已结束 ──> 幂等推送（键=task_id+status）：结果/原因/产物清单 + 下载引导
            └─ run 仍打开 ──> 静默（agent 自己会带出结果）
```

## 6. 为什么修复后这 8 条成立

1. **用户知道任务何时配置**：run_capability 创建即回 CONFIGURED，agent 立即答复。
2. **用户知道任务何时完成**：终态广播 → 通知层幂等推送（哪怕 agent run 早已结束）。
3. **Worker 忙线不会永久卡 ACCEPTED**：队列内可就地取消；对账清扫保证 attempt 不比 task 活得久；ACCEPTED 有界（SENT 掉线超时 / timeout_at / STALE）。
4. **大文件下载不会无限等待**：stall（90s 无块）+ total（900s 总账）双围栏，滴漏死链有界失败并可重试。
5. **大文件不会阻塞 heartbeat**：哈希增量分块、落盘/进程创建/扫描/上传全部离开事件循环——1GB 传输实测心跳间隙 ≤47ms。
6. **Agent 不再为长任务耗尽 Tool Call**：等待从 Tool Loop 解耦，预算只花在"理解与发起"上。
7. **Event 不会泄漏**：shield 移除后 waiter 超时即取消；全部后台任务持强引用、完成即释放。
8. **中台进度不回退**：worker seq 单调 + 服务端 seq 门禁 + attempt 快照直出。
