> **V1.7 不再重点扩展 Task，而是把 Worker 从“运行在某台电脑上的客户端”升级为“可以自动部署、自动注册、感知自身环境、持续运行并执行受控程序的标准执行节点”。**

# 1. V1.7 的核心问题

V1.6 解决的是：

> 哪台电脑执行？

V1.7 要解决的是：

> 这台电脑是否已经被正确部署？
>
> 它现在具备什么环境？
>
> 它能运行什么程序？
>
> 这个程序需要什么环境？
>
> 这个程序是一次性运行还是长期运行？
>
> 哪台电脑执行它的预计效率最高？
>
> Worker 断掉以后能不能自己恢复？

所以 V1.7 的核心已经从：

```text
Task Execution
```

进一步进入：

```text
Worker Lifecycle
+
Runtime Management
```

# 2. V1.7 核心原则

## 2.1 不修改业务 Python 是第一原则

一个已经开发好的程序：

```text
my_processor/
├── main.py
├── processors/
├── utils/
├── requirements.txt
└── ...
```

原则上不应该要求：

```text
修改 main.py
修改业务函数
import AgentHub SDK
增加 WebSocket
增加 Artifact API
增加 Worker API
```

只允许：

> **增加一份 AgentHub Runtime Configuration。**

例如：

```text
agenthub.yaml
```

这样：

```text
原 Python 程序
        +
agenthub.yaml
        ↓
AgentHub Capability
```

业务代码与平台控制逻辑彻底解耦。

# 4. AgentHub Configuration

推荐配置：

```yaml
name: data.preprocess_excel
version: 1.0.0

runtime:
  type: python
  python: ">=3.11"

execution:
  mode: once

entrypoint:
  command: main.py
  args:
    - "--input"
    - "${INPUT_DIR}"
    - "--output"
    - "${OUTPUT_DIR}"

workspace:
  input_dir: input
  output_dir: output
  log_dir: logs

environment:
  variables: {}

resources:
  estimated_duration_sec: 600
  memory_mb: 4096
  disk_mb: 20480

restart:
  policy: never
```

这个配置不是程序代码。

它是：

> **AgentHub 如何运行这个程序的声明。**

---

# 5. 为什么采用“加法配置”而不是修改 Python

例如你原来有：

```bash
python main.py --input D:\data --output D:\output
```

V1.7 不改它。

AgentHub 只负责把：

```text
D:\data
D:\output
```

转换成：

```text
Worker Workspace
```

例如：

```bash
python main.py \
  --input C:\AgentHub\workspaces\task_1001\input \
  --output C:\AgentHub\workspaces\task_1001\output
```

程序完全不知道 AgentHub 的存在。

这会带来极高兼容性。

# 9. 为什么不能让 Task 直接承担长期 Python

Task 是：

```text
一次执行
```

长期 Python 是：

```text
一个持续存在的运行实例
```

因此：

```text
Task
≠
Process
```

V1.7 应该形成：

```text
Capability
    │
    ├── OneShot Execution
    │       ↓
    │      Task
    │
    └── Persistent Execution
            ↓
        ProcessInstance
```

# 14. Worker 自身与 Python Process 必须分开

这是一个非常重要的边界：

```text
Windows Service
      ↓
AgentHub Worker
      │
      ├── Task Executor
      │
      ├── Capability Runtime
      │
      └── Process Supervisor
               │
               ├── Python A
               ├── Python B
               └── ...
```

因此：

```text
Python 挂了
≠
Worker 挂了
```

而：

```text
Worker 挂了
≠
Device 消失
```

这三个生命周期必须分开。

# 17. “Ping 通”在这里到底意味着什么

不能定义为：

```text

```


```text

```

```text

>

>

```

这可以完全自动完成。

# 30. 执行路径算法

这是 V1.7 的第二条核心主线。

你提到：

> 程序历史运行时间 + 电脑配置 + 电脑状态 → 找最优执行路径。

我建议不要一开始做 LLM 或机器学习。

第一版使用：

# Deterministic Execution Path Scoring

即：

> **确定性执行路径评分。**

---

# 31. 第一步：硬过滤

先排除不能跑的电脑。

```text
Device ONLINE
AND
READY
AND
not DRAINING
AND
Capability compatible
AND
Runtime compatible
AND
Environment satisfied
AND
Disk sufficient
```

只有符合的 Worker 才进入候选集。

---

# 32. 第二步：计算预计完成时间

核心不是：

```text
“哪个 CPU 最强？”
```

而是：

> **哪台电脑完成这一次任务的预计总耗时最低？**

定义：

```text
EstimatedCompletionTime
=
QueueWait
+
TransferTime
+
StartupTime
+
ExecutionTime
```

---

# 33. ExecutionTime 来源

优先级：

```text
历史真实运行数据
        ↓
没有历史
        ↓
Capability 配置的 estimated_duration
```

这正符合你提出的思路。

---

# 34. 历史运行时间

记录：

```text
task_id
device_id
capability
version
input_size
started_at
finished_at
duration
status
```

例如：

```text
data.preprocess_excel 1.0.0

历史 5 次
平均 720s

电脑02
历史 8 次
平均 420s

电脑03
历史 0 次
```

那么：

```text
电脑02
```

明显更有数据支撑。

---

# 35. 不要只使用简单平均值

因为：

```text
100MB
500MB
2GB
```

的运行时间完全不同。

所以至少保存：

```text
input_size
```

最好进一步：

```text
input_rows
input_file_count
input_bytes
```

然后估算：

```text
runtime_per_gb
```

例如：

```text
Worker01
1GB = 600s

Worker02
1GB = 350s
```

当新的数据：

```text
2GB
```

可以估算：

```text
Worker01 ≈ 1200s
Worker02 ≈ 700s
```

---

# 36. 历史数据不足怎么办

例如：

```text
Worker03
只有一次历史记录
```

不能完全相信。

建议：

```text
history_count
```

参与置信度。

例如：

```text
0 次：
完全使用配置基线

1~2 次：
历史 + baseline 混合

≥N 次：
主要使用历史
```

# 38. 电脑配置如何参与算法

不能简单：

```text
CPU 越大
→ 分数越高
```

而应该参与：

```text
Compatibility
+
Performance Prior
```

比如：

```text
16 cores / 32GB
```

对：

```text
large-data
```

更合适。

但是如果历史实际：

```text
8 cores Worker
实际跑得更快
```

历史应该覆盖理论硬件优势。

所以优先级：

```text
真实历史
>
环境能力
>
静态配置估算
```


只是：

> **把当前真实状态纳入执行路径选择。**

# 41. TransferTime

这也是你大文件场景必须考虑的。

例如：

```text
数据 2GB
```

Worker01：

```text
传输速度 100MB/s
≈20s
```

Worker02：

```text
10MB/s
≈200s
```

即使 Worker02 CPU 更强：

```text
也可能不应该选 Worker02。
```

所以：

```text
ExecutionPath
=
计算速度
+
数据移动成本
```

# 70. 最终的核心模型

到 V1.7，你可以把整个 AgentHub 理解成：

```text
Device
=
物理电脑

Worker
=
电脑上的 AgentHub 执行节点

Capability
=
可执行程序

agenthub.yaml
=
程序如何被 AgentHub 执行的声明

Artifact
=
输入/输出数据

Task
=
一次性执行

ProcessInstance
=
持续运行

Environment
=
这台电脑能做什么、性能如何

ExecutionResolver
=
应该让哪台电脑执行
```

# 71. V1.7 最终一句话

> **V1.7 要把“Worker”从一个连接到 AgentHub 的客户端，升级成一个可自动部署、可持续运行、可感知环境、可执行现有 Python 程序、可管理长期进程、并能参与执行路径选择的标准化计算节点。**

而你提出的三个方向正好分别对应三个核心能力：

```text
方向 1
Bootstrap
→ 解决“怎么把 Worker 快速铺到多台电脑”

方向 2
Config-driven Runtime
→ 解决“怎么让已有 Python 程序零改造接入 AgentHub”

方向 3
Execution Path Resolver
→ 解决“这一次任务到底应该放哪台电脑执行”
```

三者组合以后，V1.7 就不再只是“Worker 管理功能”，而是形成了一个真正闭环：

```text
新电脑加入
    ↓
自动部署 Worker
    ↓
采集电脑环境
    ↓
知道这台电脑能跑什么
    ↓
知道它过去跑这个程序有多快
    ↓
知道当前是不是忙
    ↓
选择预计完成时间最优的 Worker
    ↓
执行现有 Python / 影刀程序
    ↓
一次性结束 or 持久运行
    ↓
持续监控
```
